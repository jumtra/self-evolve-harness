# コーディング規約

## 設計原則

- **YAGNI**: 現在使われていない抽象化・汎化・引数・フラグを作らない。「将来使うかも」は作らない理由
- **KISS**: より単純な実装で同じ結果が得られるなら単純な方を選ぶ。過度な細分化も避ける
- **DRY**: 同じロジックの重複を避ける。ただし似ているだけで本質的に異なるものは無理に共通化しない

## TDD（テスト駆動開発）

実装は Red → Green → Refactor のサイクルで進める:

1. **Red**: 実装前に失敗するテストを書く。テストが期待する振る舞いを定義する
2. **Green**: テストを通す最小限のコードを書く。過剰な実装をしない
3. **Refactor**: テストが通ったままコードを整理する。振る舞いは変えない

- テストを先に書くことで、実装のスコープが明確になり YAGNI を自然に守れる
- 既存コードの変更時も、まず期待する振る舞いのテストを書いてから修正する

## コメント

- コードが WHAT を示し、コメントは **WHY（なぜそうしたか）** を示す
- 隠れた制約、微妙な不変条件、特定バグの回避策など、コードだけでは意図が伝わらない場合のみ記述
- コメントを消しても将来の読者が困らないなら書かない

## 関数設計

- 単一責任。1関数1目的
- 循環的複雑度を低く保つ（目安: ≤ 5）
- 早期リターン推奨（ガード節でネストを減らす）
- 副作用を最小化。純粋関数を優先する
- 処理の流れを上から下に追えるように書く

## データ構造

- イミュータブルなデータ構造を優先する
- 抽象化にはインターフェース / プロトコル等の言語機能を使う
- 辞書やマップよりも名前付きの型を使う

## エラーハンドリング

- カスタム例外 / エラー型を定義して使う
- Fail Fast: 不正な引数・状態は関数先頭でガード

## 冪等性とロバスト性

- 同じ入力で同じ結果を返す関数を書く。副作用がある場合は再実行しても安全な設計にする
- ファイル書き込みは一時ファイル + rename（アトミック書き込み）を優先する
- 既に存在するリソースの作成は、エラーではなくスキップまたは上書きで対応する
- 外部APIやファイルI/Oにはリトライとタイムアウトを設定する
- 中間状態で失敗しても、再実行で正しい最終状態に到達できるように設計する

## Linter / Formatter 規律

- linter・formatter の設定ファイルを変更しない（チーム共通設定）
- 抑制コメント（`noqa`、`type: ignore`、`fmt: off`、`eslint-disable` 等）を追加しない
- linter / formatter が指摘するエラーはコードを直して解消する。ルールを黙らせない
- 設定変更や抑制が本当に必要な場合はユーザーに相談する

## スコープ規律

タスクの範囲外の改善点を見つけた場合、その場で修正しない。代わりに以下のように記録する:

```
NOTICED BUT NOT TOUCHING:
- <ファイル:行> <改善内容>
```

タスク完了後にユーザーに報告し、別タスクとして対応するか判断を委ねる。

## 合理化に注意

以下はよくある合理化パターン。これらの思考が浮かんだら立ち止まること:

| 思考                         | 現実                                                               |
| ---------------------------- | ------------------------------------------------------------------ |
| 「このくらいならテスト不要」 | 変更にはテストを書く。例外はない                                   |
| 「後でリファクタリングする」 | 今やらないなら永遠にやらない。今やるか、スコープ外として記録する   |
| 「動いているから大丈夫」     | 動くことと正しいことは違う。型チェック・テスト・レビューで検証する |
| 「ちょっとだけ範囲外も直す」 | スコープ規律に従う。混ぜるとレビューが困難になる                   |
