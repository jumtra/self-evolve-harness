# テスト規約

## DAMP 原則（Descriptive And Meaningful Phrases）

テストコードでは DRY よりも **DAMP** を優先する。判定基準は次の1文に集約される。

> そのテスト関数だけをファイルから切り出して読んだとき、**入力値・操作・期待値のすべてが目に見えるか**。
> 1箇所でも他（ヘルパー・fixture・共通定数・基底クラス）を見に行く必要があるなら DAMP 違反。

- 各テストは **それだけ読めば何をテストしているか完全に理解できる** ように書く
- ヘルパー関数の呼び出しチェーンを辿らなくても意図が伝わること
- テスト間で多少の重複があっても、可読性・自己完結性を優先する
- テストデータはテスト関数内にインラインで書く。外部ファイルや共通定数に隠さない
- アサーションメッセージは失敗時に **何が起きたか** が即座にわかるように書く

## ヘルパー禁止（例外は外部リソース管理のみ）

**原則としてテストヘルパーを作らない・使わない。** 以下はいずれも禁止する。

| 禁止するもの                                                | なぜ                                                       |
| ----------------------------------------------------------- | ---------------------------------------------------------- |
| テストデータ生成ヘルパー・ファクトリ（`make_user()` 等）    | 入力値がテストから見えなくなる                             |
| アサーションをまとめたヘルパー（`assert_valid_user()` 等）  | 何を検証しているかがテストから見えなくなる                 |
| 共有 setup 関数の中で値を構築する                           | Arrange がテストの外に出る                                 |
| ループ・内包表記でアサーションを回す                        | 失敗時にどのケースで落ちたか分からない（→ パラメトライズ） |
| 基底テストクラス・継承による共通化                          | 継承先を辿らないと前提が分からない                         |

**許容されるのは外部リソースのライフサイクル管理のみ**（DB 接続、一時ディレクトリ、テストサーバの
起動/停止）。その場合もヘルパーに**値の生成とアサーションを含めない**。

重複は DAMP が意図的に払うコストである。20行の重複より、1行のヘルパー呼び出しで意図が隠れることを
問題とみなす。

## 命名

`<対象>_<状況>_<期待結果>` の3要素を名前に含める（言語の命名慣習に合わせる）。
名前を読んだだけで、どの入力でどうなるはずかが分かること。

- 良い: `test_parse_config_missing_required_key_raises_validation_error`
- 悪い: `test_parse_config_2` / `test_error_case` / `test_it_works`

## Good / Bad（擬似コード）

```
# Bad — 入力値とアサーションがヘルパーに隠れている
def test_discount_applied():
    order = make_order()           # 何が入っているのか読めない
    result = apply_discount(order)
    assert_discount_ok(result)     # 何を検証しているのか読めない

# Good — このテストを1つ読むだけで全部わかる
def test_apply_discount_member_with_1000_subtotal_returns_900():
    order = Order(user_type="member", subtotal=1000)   # Arrange
    result = apply_discount(order)                     # Act
    assert result.total == 900                         # Assert
```

## 構造

- AAA パターン: Arrange / Act / Assert を明確に分離
- 1テスト1アサーション（関連するアサーションのグループは可）
- Arrange セクションにはテストの前提条件を **そのテスト内で完結するように** 記述する

## セットアップ / fixture

上の「ヘルパー禁止」と同じ境界を fixture にも適用する。

- 共有セットアップは最小限に。テスト関数内で直接データを構築する方を優先する
- 外部リソースのセットアップ/テアダウンが必要なときのみ共有 fixture を使う（DB接続、tmpdir 等）
- データ生成のためだけの fixture は作らない。テスト関数内にインラインで書く
- スコープは最小限にする

## パラメトライズ

- 同一ロジックの複数入力テストはパラメトライズ機能を使う
- 各ケースにわかりやすい名前をつける

## カバレッジ

- 新規コードは80%以上を目標
- カバレッジ計測ツールで確認する

## 合理化に注意（テスト編）

以下の思考が浮かんだら立ち止まること（`coding.md` の合理化テーブルのテスト版）。

| 思考                                             | 現実                                                                       |
| ------------------------------------------------ | -------------------------------------------------------------------------- |
| 「同じ Arrange が3回出てくるから共通化しよう」   | 重複は DAMP が意図的に払うコスト。共通化すると3テストすべてが読めなくなる  |
| 「ヘルパーにすればテストが短くなる」             | 短さは目的ではない。落ちたテストを1つ読んで原因が分かることが目的          |
| 「fixture にしておけば再利用できる」             | 再利用は DRY の価値。テストでは自己完結性が優先                            |
| 「アサーションが多いのでまとめたい」             | まとめると失敗時にどの条件で落ちたか分からない。分割かパラメトライズにする |
| 「既存テストがヘルパーを使っているから合わせる」 | 既存が違反しているだけ。新規は規約に従い、既存は `NOTICED BUT NOT TOUCHING` に記録する |
