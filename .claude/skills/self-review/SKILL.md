# セルフレビュー

main ブランチからの差分を、観点別に並列ディスパッチした `reviewer` エージェントでレビューし、
集約後に敵対的検証（反証の試み）で偽陽性を落とす。

## コンテキスト収集

- 変更ファイル一覧: !`git diff main...HEAD --name-only`
- 変更差分: !`git diff main...HEAD`
- 変更統計: !`git diff main...HEAD --stat`

**差分の範囲を各 reviewer に渡す方法**: 上記で収集した差分（`git diff main...HEAD` の出力）を
そのまま各レーンの起動プロンプトに埋め込む。4レーンすべてに同一の差分テキストを渡すことで、
レーン間でレビュー対象がずれない（実行タイミングの違いで `git diff` の再実行結果が変わる事故を防ぐ）。

## 実行モデル: 4レーン並列レビュー

`reviewer` エージェントを **1メッセージ内で4回呼び出す**（Agent ツールを1メッセージに4回分含める）。
1メッセージ1エージェントを繰り返すと直列実行になり並列化の意味がなくなる（`.claude/rules/workflow.md`）。

### wave 分割は不要

`reviewer` は Edit/Write を持たない読み取り専用エージェント（`.claude/agents/reviewer.md` の
`tools: Read, Bash, WebSearch`）。ファイルを変更しないため所有ファイル衝突が原理的に起こらず、
`.claude/skills/brainstorm/references/parallel-dispatch.md` が定める所有ファイル交差判定・
wave 分割の検討は不要。4レーンは常に同一 wave（1回の一括起動）でよい。

### レーン定義

各レーンには「差分テキスト」と「このレーンの観点のみを見よ」という指示を渡す。
既存の5観点（YAGNI/KISS/DRY/Fail Fast/可読性）は漏れなく以下に配分する。

| レーン | 観点 | 旧観点との対応 |
| ------ | ---- | -------------- |
| 1. 正確性・バグ・エッジケース | ロジックの誤り、境界値・異常系の見落とし、null/空/型不整合 | 新規（旧5観点になかった正確性検証を追加） |
| 2. 設計原則・アーキテクチャ準拠 | YAGNI（不要な抽象化・汎化）、KISS（過度な複雑さ）、DRY（重複、過剰共通化）、`.claude/rules/architecture.md` の依存方向・配置規約、可読性（命名・関数長・責務単一） | YAGNI / KISS / DRY / 可読性 |
| 3. テスト網羅・DAMP 準拠 | 変更に対応するテストの有無、カバーされていないエッジケース、`.claude/rules/testing.md` の DAMP・AAA 準拠 | 新規（旧5観点になかったテスト観点を独立レーン化） |
| 4. セキュリティ・Fail Fast・入力検証 | 不正な引数・状態のガード節、インジェクション・機密情報漏洩、エラー検出が副作用後に後回しになっていないか | Fail Fast |

### 起動プロンプト雛形（レーンごとに差し替え）

```
タスク: self-review レーン<N> — <レーン名>

## 対象差分
<git diff main...HEAD の出力をそのまま貼る>

## レビュー観点（このレーンのみに集中せよ。他観点は言及不要）
<レーン定義の該当行>

## 出力形式
- 重要度: Critical / Warning / Info
- 観点: <レーン名>
- 場所: `ファイル:行番号`
- 問題: 何が問題か
- 修正案: どう直すべきか

Critical → Warning → Info の順に列挙する。問題がなければ「問題なし」と報告する。
```

## 集約（重複排除）

4レーンの出力を集めた後、以下の手順で重複を排除する:

1. 全指摘を `ファイル:行` をキーにグルーピングする
2. 同一キー内で指摘内容（問題の要旨）が実質同じものは1件にまとめる。異なる観点から
   同じ箇所の同じ問題を指摘している場合はレーン名を併記して1エントリにする
3. 同一キーで異なる問題を指摘している場合は別エントリのまま残す
4. 重要度が割れた場合は高い方（Critical > Warning > Info）を採用する

## 敵対的検証（Critical 必須・Warning/Info 任意）

集約後、**Critical 指摘は必須で**敵対的検証にかける。偽陽性（実際には問題ない指摘）を
確定前に落とすための工程。

1. Critical 指摘ごとに `reviewer` を再ディスパッチする（複数件あれば1メッセージ内でまとめて
   並列起動する。上記の「1メッセージ内で複数回呼び出す」原則と同じ）
2. 起動プロンプト:

```
タスク: self-review 敵対的検証

## 検証対象の指摘
- 場所: <ファイル:行>
- 問題: <指摘内容>
- 修正案: <修正案>

## 指示
この指摘を反証してみよ。指摘が誤りである、的外れである、既に別の理由で無害である
根拠を対象コードから探し、示せるだけ示せ。反証できなければ「反証不可、指摘は確定」と報告せよ。
```

3. 反証に成功した（＝指摘が誤りだった、または的外れだったと示された）指摘は最終レポートから除外する
4. 反証できなかった指摘は確定として最終レポートに残す
5. 反証できるか判断がつかない場合は**指摘を落とさず**、重要度を Warning に格下げして残す
   （安全側に倒す。`AGENTS.md` の「質問禁止・迷ったら安全な選択肢」に整合）
6. Warning / Info への敵対的検証は任意。時間に余裕があれば実施してよいが必須ではない

## コード品質スコア

Desloppify が利用可能な場合、品質スコアリングを実施する:

1. `desloppify scan --path . --profile ci --no-badge` を実行
2. `desloppify status --json` でスコアを取得
3. スコアをレビュー結果に含める
4. `desloppify` が未インストールの場合はスキップ

## 出力形式

敵対的検証を経て確定した指摘のみを、重要度の高い順に列挙する:

- **重要度**: Critical / Warning / Info
- **観点**: レーン名（正確性 / 設計原則・アーキテクチャ / テスト網羅 / セキュリティ・Fail Fast）
- **場所**: `ファイル:行番号`
- **問題**: 何が問題か
- **修正案**: どう直すべきか

問題がなければ「レビュー通過」と報告する。
