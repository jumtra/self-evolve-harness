# メモリ運用規約 — 共通部分（バックエンド非依存）

> `/harness-init` がこのファイルの内容と選択されたバックエンド（`file.md` / `engram.md`）を
> 連結して `.claude/rules/memory.md` を生成する。ここに書くのはバックエンド非依存のセマンティクスのみ。
> 保存・検索・索引・件数カウントの具体的な操作はバックエンド側に書く。
> 生成時はこの見出しとこの注記は出力に含めない（rules/memory.md 先頭の H1 と生成注記に集約する）。

## 設計原則

バックエンドは `/harness-init` で選択する:

| バックエンド | 内容 | 導入 |
|---|---|---|
| `file`（既定） | リポジトリローカルの `.agent-memory/`。ツール横断でそのまま共有できる | 不要 |
| `engram` | Engram MCP サーバー。ツールごとに engram MCP を登録すれば同じ記憶を共有できる | 各ツールへ MCP 登録 |

## 1 つの記憶 = 1 単位

| 項目 | 決まり |
| --- | --- |
| 識別子 | `<type>_<slug>`（例: `feedback_reply_in_japanese`, `project_home_layout`） |
| 本文 | 事実を端的に書く（要点のみ。具体例は判断に必要なら1〜数行まで）。feedback と project は **Why:** と **How to apply:** の行を付ける |
| 関連 | 他の記憶へは `[[name]]` でリンク |
| 索引 | `MEMORY.md`（またはバックエンド等価物）に `- [題](識別子) — 一言` を 1 行ずつ。中身は索引に書かない。1 行 150 字まで（索引は毎セッション載る） |
| 重複 | 新規作成の前に検索し、同じ話題があれば既存の記憶を更新する |

メタデータ（type・evolve・count）は必須:

```markdown
---
name: <kebab-case の slug>
description: <1 行の要約>
metadata:
  type: user | feedback | project | reference
---
```

| type | 何を残すか |
| --- | --- |
| `user` | ユーザー本人の属性・好み |
| `feedback` | ユーザーの指摘・修正（自己進化の入力。下記） |
| `project` | 進行中の作業・決定・決定待ちの論点・いつ何を確かめるか |
| `reference` | 外部サービスの鍵の場所・API の読み方など参照情報 |

メモリには「リポジトリに書けない今の状況」だけを残す。手順や決まりはメモリではなく
CLAUDE.md / AGENTS.md / `.claude/rules/` / `.claude/skills/` に書く。
（`file` バックエンドでは `.agent-memory/` をリポジトリにコミット共有するが、そこにも「今の状況」だけを書く。ルール類は必ず `.claude/` 側へ）

## セッション開始時の想起（義務）

索引はセッション開始時に読み込まれる（読み込み方はバックエンド側を参照）。
作業に入る前に（コンパクション直後も読み直し）、索引から関係しそうな記憶を取得して
前回の判断・未解決事項・フィードバックを確認する。

## フィードバック検知（義務）

ユーザーが修正・指摘（「そうじゃない」「こうして」「違う」等）をしたら、次のツール呼び出しの前に認識する。
同じ間違いを2回したら意識的に行動を変える。

認識したフィードバックは**その場でメモリに保存する**（保存しないと `/evolve-rules` の自動トリガーが発火しない）:

- `feedback_<slug>`（`type: feedback`）を作り、metadata に `evolve: pending` を付ける
- 本文に「何を間違えたか / ユーザーの指摘 / 正しい方法」を書き、**Why:** と **How to apply:** を付ける
- 索引に行を 1 行足す

```markdown
---
name: reply-in-japanese
description: 説明はいつも日本語で返す
metadata:
  type: feedback
  evolve: pending
  count: 1
---
```

同一パターンの再発は**新しい記憶を作らず同じ記憶に日付つきで追記**し、metadata の `count: N` を増やす
（処理済みでも再発したら `evolve: pending` に戻す）。`count` は `/evolve-rules` のルール昇格判定（3回以上でルール化）に使われる。

## セッション保存

以下のタイミングで `/save-session` を実行する:

- `/create-pr` 実行後
- `/loop` のループ完了後
- ユーザーが「終わり」「また明日」「ありがとう」等と言ったとき

`/save-session` は日誌ファイルを作らない。進行中の作業・決定待ちの論点・いつ何を確かめるかを、
該当する project メモリに追記・更新する（日付は絶対日付）。

## メモリが増えたときの移行

索引は毎セッション載る。`bash .claude/scripts/doctor.sh` が 20KB で警告する
（上限は 25KB か 200 行のどちらか先）。警告が出たら次の順で手を打つ。上の段で足りるうちは下の段へ進まない。

**段1の整理は自動実行する（ユーザーに確認しない）**: SessionStart フックの AUTO-ORGANIZE
通知（索引が20KB超）を受けたら、作業に入る前に段1をその場で実行し、整理結果を1行で報告する。
段2・段3はコスト構造が変わるため、提案して承認を得てから行う。

| 段 | 条件 | やること |
| -- | ---- | -------- |
| 1 | 索引が 20KB 超 | 索引の行を 1 行 150 字までに縮める。完了した project メモリは消して索引の行も消す。リポジトリに移した決まりのメモリも同じ |
| 2 | それでも 20KB 超（記憶が 100 件前後） | 話題ごとに索引を分ける：索引には話題ごとの見出しと 1 行の説明だけ、細かい行は話題別の索引へ。想起は話題の索引を開いてから個別の記憶を取る |
| 3 | 記憶が数百件・索引を分けても探すのに手間取る | 検索型の記憶（Engram MCP や SQLite + FTS5 の stdio MCP など）へ移す。常時載るのは索引でなくツール定義だけになり、必要な分だけ検索で引ける |

段 3 に移すときの手順:

1. 記憶を全部読み、name・本文・metadata（`evolve`・`count`）を保ったまま検索型へ 1 件ずつ登録する（移行前に現在の記憶をバックアップする）
2. `.claude/rules/memory.md` のバックエンド節（保存・検索・想起・件数カウント）を、移行先の操作に書き換える。`evolve: pending` の数え方は、移行先で同じ数が取れる式に直す
3. SessionStart のフック（健全性プローブ・AUTO-EVOLVE）と `doctor.sh` の記憶の検査、`save-session`・`evolve-rules`・`evolver` の記憶への読み書きを、移行先の操作に合わせる
4. 常時のコストが増える（ツール定義・保存や検索ごとの呼び出し）。段 2 までで足りているうちは移さない
5. 移行後は旧バックエンドの記憶を残さない（二重の正本を作らない）。索引を消して `doctor.sh` が通ることを確かめる

> `/harness-init` でバックエンドを切り替える場合もこの手順に従う（検出→合成を `/harness-init` が行う点だけが手動移行と異なる）。

## ハーネス進化（自動）

未処理フィードバック（`evolve: pending` の記憶）が3件以上たまると、SessionStart フック（`settings.json`）が
セッション冒頭に AUTO-EVOLVE 通知を注入する。未処理の数え方はバックエンド側の節を参照（フックと同じ式/問い合わせを使う）。

通知を受けたら **evolver エージェントをバックグラウンド起動**し、ユーザーの依頼と並行して処理させる
（メインセッションはブロックしない）。手動で `/evolve-rules` を実行してもよい。

反映先（ルール / スキル / エージェント / hook / CLAUDE.md・AGENTS.md）はパターンの性質から
`/evolve-rules` が自律判定する（hook は検証ゲート付き・限定操作）。

反映済みのフィードバックは `/evolve-rules` が metadata を `evolve: done` と `evolved_to: <反映先のパス>` に
書き換えるため再度カウントされない。中身が完全にリポジトリ側に移ったなら、記憶と索引の行を消してよい。
