# ハーネス進化

Engram に蓄積されたフィードバックを分析し、ハーネスを進化させる。
反映先はパターンの性質に応じて自律判定する:

- `.claude/rules/`（ルール）
- `.claude/skills/`（スキル）
- `.claude/agents/`（エージェント）
- `.claude/settings.json`（hooks）— 決定論的強制機構。限定条件下のみ（手順2d 参照）

## 実行モード

| モード | 起動条件 | 動作 |
| ------ | -------- | ---- |
| 自動 | セッション開始時の AUTO-EVOLVE 通知 | 分析 → ルール/スキル/エージェントの編集を作業ツリーに適用 → diff を報告。コミットはしない |
| 手動 | ユーザーが `/evolve-rules` を実行 | 分析 → 提案を提示 → 承認後に適用 |

自動モードでも git 管理下の編集のみ行うため、ユーザーは `git diff` で確認し、不要なら破棄できる。
**どちらのモードでも自動コミットは行わない。**

## 手順

### 1. 収集（Engram）

Engram からフィードバックとレッスンログを取得する:

- MCP ロード済み: `mem_search` で `feedback` と `lesson` を検索
- 未ロード: `engram search "feedback" --project <repo>` / `engram search "lesson" --project <repo>`

`<repo>` はリポジトリのルートディレクトリ名（`basename "$(git rev-parse --show-toplevel)"`）。

タイトル接頭辞で分類する（保存規約は `memory.md` 参照）:

- `[feedback]`: 未処理フィードバック（分析対象）
- `[lesson]`: レッスンログ（昇格判定の対象）
- `[feedback:done]`: 処理済み（対象外）

Engram が未導入（MCP なしかつ `command -v engram` 失敗）の場合は中止し、
`/init` の必須ツール導入をユーザーに案内する。

### 2. 分析

以下のパターンを特定する:

- **繰り返し出現する修正**: 同じ種類の指摘が複数回あればルール化の候補
- **暗黙知**: ルールに明文化されていないが常に従っている慣習
- **矛盾**: 既存ルールとフィードバックの間の矛盾

### 2b. レッスンログ昇格

2回出現したパターンは `[lesson]` として Engram に構造化保存する:

- 文脈: どの場面で起きたか
- 誤りパターン: 何を間違えたか
- 正しい方法: どうすべきだったか
- 予防策: 次回どう防ぐか

**3回以上出現したパターンは正式アーティファクトへ昇格させる**（反映先は
2d で判定する。ルールとは限らない）。`[lesson]` の上限は20件。
超過時は古いものから昇格または削除する。

### 2c. No-Op テスト（ルール剪定）

既存の各ルール行に対して「このルールはモデルのデフォルト動作を変えているか？」を問う:

- デフォルト動作と同じ → 削除候補（トークンと注意力の浪費）
- デフォルト動作を変えている → 維持
- 不明 → 維持するが理由（WHY）を補足する

削除・変更・WHY 補足のみを diff に反映する。「維持」判定はどこにも書き出さない
（変更がないため）。

### 2d. アーティファクト判定

3回以上出現した各パターンについて、反映先を判定する。**優先順に評価する**:

1. **既存アーティファクトの改修で対応できるか** — 既存のルール・スキル・
   エージェントの修正で足りるなら新規作成しない（スプロール防止）。
   `.claude/rules/` `/skills/` `/agents/` の一覧を必ず確認してから判定する
2. **1〜数行の制約・規約で表せる** → ルール（`.claude/rules/` の該当ファイル）
3. **複数ステップの手順を毎回繰り返している** → スキル
   （例: 毎回同じ手順のリリース作業、定型の調査フロー）
4. **独立したコンテキスト・専用ツールセット・並列実行が有効な専門役割** →
   エージェント（例: 特定観点のレビュー役、専門ドメインの検証役）
5. **file_path / コマンド文字列で機械的に検出でき、指示的ルールを入れても
   繰り返し無視される失敗** → hook（`.claude/settings.json`）。ルール（＝モデルの
   注意力頼み）からの**エスカレーション**として使う。「毎回このファイルを触って
   壊す」「commit 前に CI を回し忘れる」等、決定論的に検出・防止できるものが対象

迷ったら軽い方（ルール < スキル < エージェント）を選ぶ。hook は強制力が強く
blast radius も大きい（作業ツリーに入った時点でセッションに即効く）ため、
指示的アーティファクトで足りるなら hook にしない。hook は最後の手段。

#### スキルを作成・改修する場合

`/create-skill` のテンプレート・テスト・セキュリティ検証手順に従う。
ただし自動モードでは以下を読み替える:

- 要件定義のヒアリングは行わず、フィードバック証拠（何を・いつ・どう
  間違えたか）を要件として使う
- 配置前にドライランで手順が実行可能なことを確認する。サブエージェント試行が
  望ましいが、書き込み先を用意できない環境では机上シミュレーション
  （手順を具体シナリオに当てて1ステップずつ検証）で代替してよい
- skillspector 未導入時のスキップは「ユーザーに案内」ではなく完了報告と
  changelog に記載する

#### エージェントを作成・改修する場合

`.claude/agents/*.md` の既存規約に従う:

- frontmatter: `name`（kebab-case）/ `description`（いつ使うか）/ `model` / `tools`（最小限）
- 本文: 役割・手順・観点を簡潔に。既存の `reviewer.md` / `fixer.md` を文体の参考にする

#### hook を作成・改修する場合

hook の記述規約は `.claude/skills/init/shared/hooks-boilerplate.md` を単一ソースとして
参照する（stdin JSON パースのイディオム、`exit 2` は PreToolUse のみ、パース曖昧時は
fail-open 等）。ここには複製しない。

**操作範囲（限定）**:

- 新規 hook の追加、および evolve が過去に追加した hook（`docs/harness-changelog.md`
  で追跡）の改修のみ行う
- `/init` 生成の安全フック（破壊的コマンドブロック / 機密ファイルブロック / 設定保護 /
  フォーマッタ / アーキテクチャ守衛 / CI ゲート）と、evolve 由来でない既存 hook の
  **削除・改変はしない**。必要と判断しても適用せず報告に留める

**必須検証ゲート**（自動・手動どちらのモードでも、以下を全て通過して初めて適用する。
一つでも失敗したら適用せず「見送り」として報告する）:

1. **JSON 妥当性**: 変更後の `settings.json` を `python3 -m json.tool .claude/settings.json`
   に通し、妥当な JSON であることを確認する
2. **プレースホルダ検査**: hook の command に未展開トークン（`<...>` 等）が残っていない
   ことを確認する。JSON はコメント不可のため、未展開のまま入るとリテラル実行で破綻する
3. **dry-run**: hook のシェルをサンプル stdin JSON（対象イベントの `tool_input` を
   模したもの）で実行し、想定通りに `exit 0` / `exit 2` することを確認する。PreToolUse
   ブロック系は「ブロック対象で exit 2・非対象で exit 0」の両方を確認する
4. **fail-open**: パースに失敗する入力でも `exit 0`（誤ブロックで作業を止めない）で
   あることを確認する

> hook は作業ツリーの `settings.json` に入った時点で以降のツール呼び出しに即座に効く
> （コミット前でも）。壊れた hook はセッション自体を止めるため、上記ゲートは省略不可。

### 2e. 前回進化の効果検証（AHE: Predicted Impact の答え合わせ）

新しい変更を決める前に、**前回の evolve が効いたか**を確認する。これを怠ると
「効かない変更を積み増すだけ」になり、AHE 原則（予測効果の検証）が空文になる。

1. `docs/harness-changelog.md` の直近エントリを読み、各変更の対象パターン
   （root cause / feedback 要約）と適用日を取り出す
2. 各変更について、**適用日以降に同じ root cause の `[feedback]` が再発したか**を
   Engram で確認する（`mem_search` / `engram search` で該当キーワード検索し、
   `[feedback]` / `[feedback:done]` の保存日時が適用日より後のものを数える）
3. 判定を changelog の該当エントリに追記する:
   - **効果あり（再発なし）**: そのまま維持
   - **効果なし（再発あり）**: 変更が不十分。強化（ルール→hook へのエスカレーション等）
     を今回の候補に加えるか、逆効果ならロールバック候補として報告する
4. ロールバックは自動適用せず、根拠（再発した feedback）とともに報告する

> 検証は「前回エントリがある場合のみ」。初回実行や changelog が空なら本ステップはスキップ。

### 3. 適用（自動）/ 提案（手動）

判定結果に基づく変更を diff 形式でまとめる:

- 新規ルールの追加（レッスンログ昇格を含む）
- 既存ルール・スキル・エージェントの修正・補足
- 新規スキル・エージェントの作成（2d の判定に基づく）
- 新規 hook の追加・自作 hook の改修（2d の判定に基づく。**必須検証ゲート通過が前提**）
- 不要になったルールの削除（No-Op テスト結果を含む）

各変更には **AHE 4項目**（`references/ahe-principles.md` 参照）を必須とする:

1. Failure Evidence（失敗の証拠）
2. Root Cause（根本原因）
3. Fix（修正内容）
4. Predicted Impact（予測される効果）

自動モードはこの diff をそのまま適用して報告する。手動モードは提示して承認を待つ。
hook の変更は検証ゲートを通過したものだけを適用対象に含める。ゲートで落ちた hook 候補は
「見送り」として理由（どのゲートで落ちたか）とともに報告する。

### 4. 処理済みマーク

反映した `[feedback]` は再カウントされないようにする:

- MCP: `mem_update` でタイトルを `[feedback:done] ...` に変更
- CLI: 処理した各 `[feedback]` に対応する `[feedback:done] <同じ要約>` を
  `engram save` で1件ずつ追加保存する（非破壊・常に実行可能）。
  AUTO-EVOLVE フックは「`[feedback]` 件数 − `[feedback:done]` 件数」を未処理数と
  みなすため、これで再発火しなくなる
- 元エントリの削除（`mem_delete` / `engram delete <obs_id>`）は任意の掃除であり、
  実行できなくても問題ない
- 正式アーティファクトへ昇格した `[lesson]` も同様に処理する

これを怠ると AUTO-EVOLVE 通知が毎セッション発火し続ける。

### 5. ログ

`docs/harness-changelog.md` に以下を追記:

```markdown
## YYYY-MM-DD

### 追加/変更されたアーティファクト

- `<rules/skills/agents/settings.json のファイルパス>`: <変更内容>
  - 根拠: <フィードバックメモリのサマリ>
  - 予測効果: <この変更で何が改善されるか（AHE 4項目の Predicted Impact）>
  - 検証: <次回 evolve 時に手順2e で記入。「未検証」→「効果あり(再発なし)」/「効果なし(再発:件数)」>
```

hook を追加・改修した場合は、後で「自作 hook」と識別できるよう
**event（PreToolUse 等）・matcher・目的**を必ず記録する（手順2d の操作範囲判定で参照する）。
`検証:` 行は手順2e が次回実行時に更新するため、初回は必ず「未検証」で残すこと。

### 6. コミット

コミットはユーザーが diff を確認してから行う。自動コミットは行わない。

## 自動トリガーの仕組み

`settings.json` の SessionStart フックが未処理 `[feedback]` 件数を数え、
**3件以上**ならセッション冒頭に AUTO-EVOLVE 通知を注入する。

通知を受けたメインセッションは、**evolver エージェント**（`.claude/agents/evolver.md`）
を Agent ツールでバックグラウンド起動し、自分はユーザーの依頼に着手する。
evolver がこのスキルを自動モードで実行し、完了報告が届いたらユーザーに要約を伝える。
メインセッションがこのスキルを直接実行するのは手動モード（ユーザーが
`/evolve-rules` と入力したとき）のみ。
