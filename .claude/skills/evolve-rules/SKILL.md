# ハーネス進化

ファイルメモリ（`memory/`）に蓄積されたフィードバックを分析し、ハーネスを進化させる。
反映先はパターンの性質に応じて自律判定する:

- `.claude/rules/`（ルール）
- `.claude/skills/`（スキル）
- `.claude/agents/`（エージェント）
- `CLAUDE.md` / `AGENTS.md`（プロジェクト全体の決まり。CLAUDE.md は AGENTS.md を読み込む）
- `.claude/settings.json`（hooks）— 決定論的強制機構。限定条件下のみ（手順2d 参照）

## 実行モード

| モード | 起動条件                            | 動作                                                                                      |
| ------ | ----------------------------------- | ----------------------------------------------------------------------------------------- |
| 自動   | セッション開始時の AUTO-EVOLVE 通知 | 分析 → ルール/スキル/エージェントの編集を作業ツリーに適用 → diff を報告。コミットはしない |
| 手動   | ユーザーが `/evolve-rules` を実行   | 分析 → 提案を提示 → 承認後に適用                                                          |

自動モードでも git 管理下の編集のみ行うため、ユーザーは `git diff` で確認し、不要なら破棄できる。
**どちらのモードでも自動コミットは行わない。**

## 手順

### 1. 収集（ファイルメモリ + 実行ログ）

メモリディレクトリからフィードバックとレッスンログを取得する（置き場所と保存規約は `memory.md` 参照）:

```bash
ROOT=$(dirname "$(git rev-parse --path-format=absolute --git-common-dir)")
MEMDIR="$HOME/.claude/projects/$(echo "$ROOT" | sed 's#/#-#g')/memory"
grep -l '^ *evolve: pending' "$MEMDIR"/*.md 2>/dev/null   # 未処理（分析対象）
grep -l '^ *kind: lesson' "$MEMDIR"/*.md 2>/dev/null      # レッスンログ
```

見つかったファイルを Read し、metadata で分類する:

- `type: feedback` かつ `evolve: pending`: 未処理フィードバック（分析対象。`count` が再発回数）
- `kind: lesson`（`lesson_<slug>.md`）: レッスンログ（昇格判定の対象）
- `evolve: done`: 処理済み（対象外。手順2e の再発確認では参照する）

`evolve:` を持たない古い feedback メモリも、既存ルールとの矛盾・暗黙知の確認には使ってよい。

メモリディレクトリが存在しない場合は中止し、`memory.md` の置き場所の求め方を確認するよう報告する
（未処理が0件なら分析対象なしとして手順2c・2e のみ行ってよい）。

#### 実行ログの集計（証拠源その2）

メモリのフィードバックは「気づき」ベースの証拠。`.claude/harness-log.jsonl`
（hook が dispatch / commit / session_start を自動記録する実行ログ。git 管理外）は
「実測」ベースの証拠として並列に使う。集計例（`python3` 標準ライブラリのみで完結）:

```bash
python3 -c "
import json, collections, os
path = '.claude/harness-log.jsonl'
if not os.path.exists(path) or os.path.getsize(path) == 0:
    print('未計測: .claude/harness-log.jsonl が無いか空です')
else:
    events, agents = collections.Counter(), collections.Counter()
    with open(path) as f:
        for line in f:
            line = line.strip()
            if not line:
                continue
            try:
                d = json.loads(line)
            except Exception:
                continue
            events[d.get('event')] += 1
            if d.get('event') == 'dispatch':
                agents[d.get('agent', 'unknown')] += 1
    print('events:', dict(events))
    print('dispatch by agent:', dict(agents))
"
```

`grep`/`sort`/`uniq` でも代替できる:

```bash
f=.claude/harness-log.jsonl
[ -s "$f" ] && grep -o '\"event\":\"[^\"]*\"' "$f" | sort | uniq -c
[ -s "$f" ] && grep -o '\"agent\":\"[^\"]*\"' "$f" | sort | uniq -c
```

注意: `commit` イベントは「Bash 実行コマンド文字列に `git commit` を含む」だけで
発火するため、実行しただけでコミットに至らなかった呼び出しも混ざる。
**件数は目安であり厳密なコミット数ではない**。

解釈例（分析の手がかりであり断定ではない。他の証拠と突き合わせて判断する）:

- `fixer` の dispatch 比率が高い → 3ストライクが頻発している＝`debugging.md` か
  該当ルールが機能していない証拠
- `implementer` の dispatch 件数に対し `reviewer` の dispatch がほとんど無い →
  レビュー工程が飛ばされている証拠

ログファイルが無い、または0行の場合は**「未計測」として扱い、分析を中止しない**
（メモリディレクトリが無いときの中止とは異なる扱い。ログはあくまで補助証拠であり、無くても
メモリ側の証拠だけで手順2以降を継続できる）。

### 2. 分析

以下のパターンを特定する:

- **繰り返し出現する修正**: 同じ種類の指摘が複数回あればルール化の候補
- **暗黙知**: ルールに明文化されていないが常に従っている慣習
- **矛盾**: 既存ルールとフィードバックの間の矛盾

### 2b. レッスンログ昇格

2回出現したパターン（`count: 2`）は `lesson_<slug>.md` としてメモリに構造化保存する
（`type: feedback`・`kind: lesson`・`evolve: pending`。元の feedback ファイルへ `[[name]]` でリンクする）:

- 文脈: どの場面で起きたか
- 誤りパターン: 何を間違えたか
- 正しい方法: どうすべきだったか
- 予防策: 次回どう防ぐか

**3回以上出現したパターンは正式アーティファクトへ昇格させる**（反映先は
2d で判定する。ルールとは限らない）。lesson ファイルの上限は20件。
超過時は古いものから昇格または削除する。

### 2c. No-Op テスト（ルール剪定）

既存の各ルール行に対して「このルールはモデルのデフォルト動作を変えているか？」を問う:

- デフォルト動作と同じ → 削除候補（トークンと注意力の浪費）
- デフォルト動作を変えている → 維持
- 不明 → 維持するが理由（WHY）を補足する

削除・変更・WHY 補足のみを diff に反映する。「維持」判定はどこにも書き出さない
（変更がないため）。

### 2d. アーティファクト判定

3回以上出現した各パターンについて、反映先を判定する。**優先順に評価する**:

1. **既存アーティファクトの改修で対応できるか** — 既存のルール・スキル・
   エージェントの修正で足りるなら新規作成しない（スプロール防止）。
   `.claude/rules/` `/skills/` `/agents/` の一覧と `CLAUDE.md` / `AGENTS.md` を必ず確認してから判定する。
   プロジェクト固有の手順は該当するプロジェクトスキルの改修を第一候補にする
2. **1〜数行の制約・規約で表せる** → ルール（`.claude/rules/` の該当ファイル）。
   作業の種類を問わずプロジェクト全体に効く決まり（言葉づかい・報告の言語・UI の方針等）は
   `AGENTS.md`（CLAUDE.md から読み込まれる）
3. **複数ステップの手順を毎回繰り返している** → スキル
   （例: 毎回同じ手順のリリース作業、定型の調査フロー）
4. **独立したコンテキスト・専用ツールセット・並列実行が有効な専門役割** →
   エージェント（例: 特定観点のレビュー役、専門ドメインの検証役）
5. **file_path / コマンド文字列で機械的に検出でき、指示的ルールを入れても
   繰り返し無視される失敗** → hook（`.claude/settings.json`）。ルール（＝モデルの
   注意力頼み）からの**エスカレーション**として使う。「毎回このファイルを触って
   壊す」「commit 前に CI を回し忘れる」等、決定論的に検出・防止できるものが対象

迷ったら軽い方（ルール < スキル < エージェント）を選ぶ。hook は強制力が強く
blast radius も大きい（作業ツリーに入った時点でセッションに即効く）ため、
指示的アーティファクトで足りるなら hook にしない。hook は最後の手段。

#### スキルを作成・改修する場合

`/create-skill` のテンプレート・テスト・セキュリティ検証手順に従う。
ただし自動モードでは以下を読み替える:

- 要件定義のヒアリングは行わず、フィードバック証拠（何を・いつ・どう
  間違えたか）を要件として使う
- 配置前にドライランで手順が実行可能なことを確認する。サブエージェント試行が
  望ましいが、書き込み先を用意できない環境では机上シミュレーション
  （手順を具体シナリオに当てて1ステップずつ検証）で代替してよい
- skillspector 未導入時のスキップは「ユーザーに案内」ではなく完了報告と
  changelog に記載する

#### エージェントを作成・改修する場合

`.claude/agents/*.md` の既存規約に従う:

- frontmatter: `name`（kebab-case）/ `description`（いつ使うか）/ `model` / `tools`（最小限）
- 本文: 役割・手順・観点を簡潔に。既存の `reviewer.md` / `fixer.md` を文体の参考にする

#### hook を作成・改修する場合

hook の記述規約は `.claude/skills/harness-init/shared/hooks-boilerplate.md` を単一ソースとして
参照する（stdin JSON パースのイディオム、`exit 2` は PreToolUse のみ、パース曖昧時は
fail-open 等）。ここには複製しない。

**操作範囲（限定）**:

- 新規 hook の追加、および evolve が過去に追加した hook（`docs/harness-changelog.md`
  で追跡）の改修のみ行う
- `/harness-init` 生成の安全フック（破壊的コマンドブロック / 機密ファイルブロック / 設定保護 /
  フォーマッタ / アーキテクチャ守衛 / CI ゲート）と、evolve 由来でない既存 hook の
  **削除・改変はしない**。必要と判断しても適用せず報告に留める

**必須検証ゲート**（自動・手動どちらのモードでも、以下を全て通過して初めて適用する。
一つでも失敗したら適用せず「見送り」として報告する）:

1. **JSON 妥当性**: 変更後の `settings.json` を `python3 -m json.tool .claude/settings.json`
   に通し、妥当な JSON であることを確認する
2. **プレースホルダ検査**: hook の command に未展開トークン（`<...>` 等）が残っていない
   ことを確認する。JSON はコメント不可のため、未展開のまま入るとリテラル実行で破綻する
3. **dry-run**: hook のシェルをサンプル stdin JSON（対象イベントの `tool_input` を
   模したもの）で実行し、想定通りに `exit 0` / `exit 2` することを確認する。PreToolUse
   ブロック系は「ブロック対象で exit 2・非対象で exit 0」の両方を確認する
4. **fail-open**: パースに失敗する入力でも `exit 0`（誤ブロックで作業を止めない）で
   あることを確認する

> hook は作業ツリーの `settings.json` に入った時点で以降のツール呼び出しに即座に効く
> （コミット前でも）。壊れた hook はセッション自体を止めるため、上記ゲートは省略不可。

### 2e. 前回進化の効果検証（AHE: Predicted Impact の答え合わせ）

新しい変更を決める前に、**前回の evolve が効いたか**を確認する。これを怠ると
「効かない変更を積み増すだけ」になり、AHE 原則（予測効果の検証）が空文になる。

1. `docs/harness-changelog.md` の直近エントリを読み、各変更の対象パターン
   （root cause / feedback 要約）と適用日を取り出す
2. 各変更について、**適用日以降に同じ root cause のフィードバックが再発したか**を
   メモリで確認する（`grep -ril "<該当キーワード>" "$MEMDIR"` で探し、該当ファイルの
   日付つき追記のうち適用日より後のものを数える。`evolve: done` から `pending` に戻ったものも再発）
3. 判定を changelog の該当エントリに追記する:
   - **効果あり（再発なし）**: そのまま維持
   - **効果なし（再発あり）**: 変更が不十分。強化（ルール→hook へのエスカレーション等）
     を今回の候補に加えるか、逆効果ならロールバック候補として報告する
4. ロールバックは自動適用せず、根拠（再発した feedback）とともに報告する

> 検証は「前回エントリがある場合のみ」。初回実行や changelog が空なら本ステップはスキップ。

### 2f. スキルの棚卸し（毎回）

`bash .claude/scripts/doctor.sh` の skills 節（説明の大きさ・使用回数。使用は実行ログの `skill` イベント）を読み、スキルが増えすぎていないか確かめる。ログが 30 日分に満たなければ見送る。

| 状況 | 扱い |
| ---- | ---- |
| 30 日使われていない・手でしか呼ばない | **自動**: `disable-model-invocation: true` を付ける（戻せる。毎ターンの説明コストが消える） |
| 手順が決まった処理だけで判断が要らない | スクリプト・タスクランナー（moon・make など）に移す案を出す |
| 2 つ以上が同じ場面で使われている・説明が重なる | 統合案を出す（残す方と移す中身を明記） |
| 90 日使われていない | 削除案を出す |

削除・統合・スクリプト化は **提案として diff を出し、承認を待つ**（自動では消さない）。

### 3. 適用（自動）/ 提案（手動）

判定結果に基づく変更を diff 形式でまとめる:

- 新規ルールの追加（レッスンログ昇格を含む）
- 既存ルール・スキル・エージェントの修正・補足
- 新規スキル・エージェントの作成（2d の判定に基づく）
- 新規 hook の追加・自作 hook の改修（2d の判定に基づく。**必須検証ゲート通過が前提**）
- 不要になったルールの削除（No-Op テスト結果を含む）

各変更には **AHE 4項目**（`references/ahe-principles.md` 参照）を必須とする:

1. Failure Evidence（失敗の証拠）
2. Root Cause（根本原因）
3. Fix（修正内容）
4. Predicted Impact（予測される効果）

自動モードはこの diff をそのまま適用して報告する。手動モードは提示して承認を待つ。
hook の変更は検証ゲートを通過したものだけを適用対象に含める。ゲートで落ちた hook 候補は
「見送り」として理由（どのゲートで落ちたか）とともに報告する。

### 4. 処理済みマーク

反映したフィードバックは再カウントされないようにする。該当メモリファイルの metadata を書き換える:

```yaml
metadata:
  type: feedback
  evolve: done
  evolved_to: <反映先のパス（例: .claude/skills/<name>/SKILL.md）>
  count: 3
```

- AUTO-EVOLVE フックは `evolve: pending` の行を持つファイル数を未処理数とみなすため、これで再発火しなくなる
- 中身が完全にリポジトリ側に移った（メモリに「リポジトリに書けない今の状況」が残っていない）なら、
  ファイルを消して `MEMORY.md` の該当行も消してよい（任意の掃除）。今の状況が残るなら
  ファイルは残し、反映済みの部分だけ削って `evolved_to` で反映先を示す
- 正式アーティファクトへ昇格した lesson ファイルも同様に処理する
- 反映しなかった（見送った）フィードバックは `evolve: pending` のまま残す

これを怠ると AUTO-EVOLVE 通知が毎セッション発火し続ける。

### 5. ログ

`docs/harness-changelog.md` に以下を追記:

```markdown
## YYYY-MM-DD

### 追加/変更されたアーティファクト

- `<rules/skills/agents/settings.json/CLAUDE.md/AGENTS.md のファイルパス>`: <変更内容>
  - 根拠: <フィードバックメモリのサマリ>
  - 予測効果: <この変更で何が改善されるか（AHE 4項目の Predicted Impact）>
  - 検証: <次回 evolve 時に手順2e で記入。「未検証」→「効果あり(再発なし)」/「効果なし(再発:件数)」>
```

hook を追加・改修した場合は、後で「自作 hook」と識別できるよう
**event（PreToolUse 等）・matcher・目的**を必ず記録する（手順2d の操作範囲判定で参照する）。
`検証:` 行は手順2e が次回実行時に更新するため、初回は必ず「未検証」で残すこと。

### 6. コミット

コミットはユーザーが diff を確認してから行う。自動コミットは行わない。

## 自動トリガーの仕組み

`settings.json` の SessionStart フックが未処理フィードバック件数を数え、
**3件以上**ならセッション冒頭に AUTO-EVOLVE 通知を注入する。数え方は次の式:

```bash
grep -l '^ *evolve: pending' "$MEMDIR"/*.md 2>/dev/null | wc -l
```

通知を受けたメインセッションは、**evolver エージェント**（`.claude/agents/evolver.md`）
を Agent ツールでバックグラウンド起動し、自分はユーザーの依頼に着手する。
evolver がこのスキルを自動モードで実行し、完了報告が届いたらユーザーに要約を伝える。
メインセッションがこのスキルを直接実行するのは手動モード（ユーザーが
`/evolve-rules` と入力したとき）のみ。
