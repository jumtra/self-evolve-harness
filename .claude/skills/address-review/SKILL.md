# PR レビュー対応

`/create-pr` で作成した PR に付いたレビューコメントを取り込み、分類 → 対応方針の承認 →
修正 → 再push → 解決報告までを型にします。

**引数（任意）:** "$ARGUMENTS"（PR番号。省略時は現在のブランチに紐づくPRを対象にする）

## コンテキスト収集

- 現在のブランチ: !`git branch --show-current`
- 対象PRの基本情報: !`gh pr view $ARGUMENTS --json number,title,url,state,reviewDecision`
- レビュー本体（Approve / Request changes 等の意思表示）: !`gh pr view $ARGUMENTS --json reviews`
- インラインコメント（ファイル・行に紐づく指摘）: !`gh api repos/{owner}/{repo}/pulls/$ARGUMENTS/comments`
- 会話スレッドのコメント（PR全体への一般コメント）: !`gh pr view $ARGUMENTS --comments`

`$ARGUMENTS` が空の場合は、`gh pr view --json number` で現在のブランチのPR番号を先に解決してから
上記コマンドに補う。

## 手順

1. **状態確認**
   - PRが存在しない、またはすでにマージ済みの場合はその旨を報告して終了する
   - `reviewDecision` が `APPROVED` かつ未解決の指摘が0件なら、対応不要である旨を報告して終了する

2. **指摘の分類**
   収集したレビュー・コメントを1件ずつ、以下の3区分に分類する。分類には必ず根拠
   （誰の・どのレビュー状態のコメントか）を添える。

   - **対応必須（blocking）**: `Request changes` レビューに紐づく指摘、または明確な不具合・
     仕様違反を指す指摘
   - **議論が必要**: 意図や仕様の解釈が割れている、複数の対応案がありうる指摘
   - **対応不要（nit / 意見）**: 個人の好み・任意提案で、コードの正しさに影響しない指摘。
     対応不要と判断した場合は理由を明示する（無視ではなく判断であることを示す）

   出力形式:
   ```
   - 区分: 対応必須 / 議論が必要 / 対応不要
   - 指摘者: <レビュアー>（レビュー状態: <APPROVED/CHANGES_REQUESTED/COMMENTED>）
   - 場所: <ファイル:行 または PR全体>
   - 指摘内容: <要約>
   - 根拠: <なぜこの区分か>
   ```

3. **技術的に疑わしい指摘の扱い**
   指摘が技術的に誤っている可能性がある場合、盲従しない。対象コード・仕様・公式ドキュメント等の
   根拠を確認したうえで、以下のいずれかを行う:
   - 根拠を示して指摘への反論を用意する（対応方針の提示時にあわせて示す）
   - 確認が取れない場合は「確認事項」として対応方針に含め、独断で却下・反論しない

4. **対応方針の提示とユーザー承認**
   分類結果と各指摘への対応方針（修正する / 反論する / 確認事項として残す / 対応不要とする）を
   まとめて提示し、**ユーザーの承認を得てから修正に着手する**。他人（レビュアー）の指摘を
   確認なく却下しない。承認前に修正を開始してはならない。

5. **修正の実行**
   承認された方針に沿って、指摘ごとに以下のループを回す（`.claude/rules/workflow.md` の
   ループ協議に準拠）:
   1. 該当箇所を修正する
   2. CLAUDE.md の `CI_CHECK_CMD` を実行する
   3. 通過したら、その指摘に対するコミットを作成する（`.claude/rules/workflow.md` のコミット
      規約に従う：動詞始まり・50文字以内・動作未検証の場合は `WIP:` を使わない。ここでは
      CI通過済みのみコミットするため通常のプレフィクスでよい）
   4. 失敗したら修正 → 再実行を繰り返す。同じエラーが2回連続したら深追いせず、未解決として
      報告に残す

   複数の指摘をまとめて1コミットにしてよいのは、変更が密接に関連する場合のみ。可能な限り
   指摘単位でコミットを分け、後述の解決報告で1件ずつ紐づけられるようにする。

6. **再pushと解決報告**
   - すべての対応が完了したら `git push origin HEAD` でリモートへ反映する
   - `gh pr comment $ARGUMENTS --body "..."` で、各指摘への対応結果を1件ずつ紐づけて報告する。
     各エントリには対応内容と、根拠となるCI通過出力（証拠）を添える
     （`.claude/rules/workflow.md` の Evidence-Before-Assertion に従い、証拠なき「対応済み」
     報告はしない）
   - 「議論が必要」「確認事項」に区分した指摘は、対応した/していないに関わらず、その理由と
     現状（未解決なら誰の判断待ちか）を明記する

7. **完了条件**
   以下をすべて満たした時点で完了とする:
   - 対応必須（blocking）の指摘が0件（対応済み、または承認済みの反論で解消済み）
   - CI が green（証拠となる実行結果を保持している）
   - 対応不要・議論が必要と判断した指摘は、理由がPRコメントに記録済み

8. **セッション保存**
   完了後、`/save-session` を実行してセッションコンテキストを永続化する
