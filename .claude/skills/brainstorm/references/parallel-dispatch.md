# 並列ディスパッチ・プロトコル

オーケストレータ（メインセッション）が、承認済み実装計画の wave を並列実行する手順。

- ワーカー側の契約: `.claude/agents/implementer.md`
- 判定基準の要約（常時ロード）: `.claude/rules/workflow.md`

## 0. 前提

- 並列化の単位は **wave**。同一 wave のタスクは同時に走る
- 既定の並列度上限は **4**（同時に起動する数。wave の分割数ではない）
- ワーカーはコミットせず、全体 CI も実行しない。どちらも barrier でオーケストレータが行う

## 1. 独立性の判定

2つのタスクを同一 wave に入れてよいのは、以下を**すべて**満たすときだけ。

1. **所有ファイル集合が互いに素**（同じファイルを1つも共有しない）
2. **依存関係がない**（一方の出力を他方が入力にしない）
3. **共有状態を壊し合わない**（同一のスキーマ定義・設定ファイル・グローバル登録簿・
   スナップショットに触らない）

判定結果は表にして計画書に残す。

| タスク | 所有ファイル | 依存 | wave |
| ------ | ------------ | ---- | ---- |

- 交差があるタスクは**後続 wave に落とす**。同一 wave に押し込まない
- 判断がつかないものは直列にする（`workflow.md`: 迷ったら直列）

## 2. wave 編成

1. 依存のないタスクを wave 1 に置く
2. wave 1 内で所有ファイルが交差するものを後続 wave に落とす
3. 残りを、依存が解けた順に wave 2, 3 … へ割り当てる
4. wave 内のタスク数が並列度上限を超える場合は、その wave 内で2回に分けて起動する
   （wave 自体は分割しない。barrier は wave 単位）

**縮退**: 全タスクが同じファイルを触る場合、各 wave が1タスク＝直列になる。これは正常動作。
並列化できないことを異常扱いして、無理にファイルを分割しない。

## 3. コンテキストパック（起動プロンプトの雛形）

ワーカーは独立したコンテキストで動く。「さっき話した」は通じないので、必要な情報は
すべてプロンプトに入れる。

```
タスク: <実装計画 #N のタスク名>

## 目的
<1-3文。計画書の該当行から転記>

## 所有ファイル（これ以外は変更禁止）
- <path1>
- <path2>

## 完了条件
- <検証可能な条件>

## スコープテスト
<このタスクの範囲に絞ったテストコマンド。全体 CI は実行しないこと>

## 参照ルール
- .claude/rules/coding.md（TDD・設計原則）
- .claude/rules/testing.md（DAMP・AAA）
- <architecture.md があれば追記>

## 前 wave からの申し送り
<なければ「なし」>
```

**一括起動**: 1メッセージ内で Agent ツールを複数回呼ぶ。1メッセージ1エージェントを
繰り返すと直列になり、並列化の意味がなくなる。

## 4. wave barrier（全ワーカー完了後）

この順番を守る。CI を先に回すと、境界逸脱の混入を見逃す。

1. **境界検証**: `git diff --name-only` と `git status --porcelain` を取り、変更集合が
   その wave の所有ファイル集合の和に収まっているか確認する
2. **報告の突合**: 各ワーカーの結果種別を確認する（成功 / 失敗 / 部分完了 / 境界外 / 入力不足）
3. **全体 CI**: `CI_CHECK_CMD` を1回だけ実行する
4. **コミット**: 通過したら wave 単位でコミットする（`workflow.md` のコミット規約）。
   CI の通過出力を証拠として残す（Evidence-Before-Assertion）
5. **次 wave へ**: 各ワーカーの申し送りを次 wave のプロンプトに載せる

## 5. 異常系

| 状況                             | 対処                                                                                                                                       |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| 一部のワーカーが失敗             | 成功分の変更は残す。失敗タスクのみ再ディスパッチし、解決するまでその wave の barrier を閉じない。同一エラー2回で fixer に委譲              |
| 「境界外の変更が必要」で返った   | 計画の所有ファイル集合を見直す。必要なら該当タスクを後続 wave に落とし、依存先の後に再実行する。他ファイルを勝手に触らせない                |
| 「入力不足」で返った             | プロンプトの欠落項目を埋めて再ディスパッチする。ワーカーの落ち度ではない                                                                    |
| 境界検証で逸脱を検出             | 差分を確認し、タスクに必要なら計画を更新して受け入れ、不要なら `git checkout -- <path>` で戻す。**次 wave を起動する前に**整合させる         |
| barrier の CI が赤               | ci-triage で失敗を分類し、由来ワーカーのタスクを特定してから修正する。推測で直さない                                                        |
| ワーカーの結果が空・応答不能     | そのタスクは未実行として扱う。作業ツリーに中途半端な変更が残っていないか確認してから再ディスパッチ                                          |

## 6. worktree 隔離（例外措置）

原則はファイル所有権の排他。それでも同一ファイルを触るタスクを並列したい場合のみ使う。

1. 各ワーカーを `isolation: "worktree"` で起動する（隔離された作業ツリーで実行される）
2. 各ワーカーの差分を順に取り込み、コンフリクトはオーケストレータが解消する
3. 取り込み後に全体 CI を1回回す

コストが高く（ツリー作成 + マージ解消）、コンフリクト解消の判断がオーケストレータに集中する。
**まず wave の分割で解けないかを検討する**。分割で解けるなら worktree は使わない。
生成物は `.claude/worktrees/`（`.gitignore` 済み）。

## 7. 並列化しないもの

- コミット・ブランチ操作（barrier でオーケストレータのみ）
- 全体 CI の実行（同一ツリーで同時に走らせると互いに汚染する）
- 同一ファイルへの書き込み（wave 分割、それが無理なら worktree）
- 依存のあるタスク（迷ったら直列）
