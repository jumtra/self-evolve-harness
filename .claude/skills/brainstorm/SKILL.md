# 要件定義 → 実装計画 → 自律実行（detail）/ 確認 → 実装（simple）

## フェーズ0: モード選択

引数 `/brainstorm detail` / `/brainstorm simple` でモード指定済みならそのまま使う。
`non-stop` も付いていれば後述の non-stop 運用に入る。引数がなければ、まずユーザーに
モードを確認する（1問だけ。選択式を優先）:

| モード | 流れ | 向くケース |
|---|---|---|
| **detail**（既定） | 要件定義書→実装計画書を `docs/specs/` に作成・承認 → wave 並列の自律実行 | 複数ファイル・新機能・判断余地の大きい変更 |
| **simple** | 一問一答の確認（要約の承認のみ）→ 実装 → 動作観点のレビュー | 小規模変更・要件がほぼ明確な修正 |

### non-stop 運用（`/brainstorm <detail|simple> non-stop`）

途中でヒアリング・承認を挟まず、完了まで止まらないモード:

- モード選択・ヒアリング・承認ゲートをすべてスキップし、フェーズを通しで実行する
- 判断に迷う点は**安全な選択肢を採用**し、要件定義書/確認要約に「non-stop で採用した判断」として記録する
- detail non-stop: 要件定義書・実装計画書は作成するが承認を待たずフェーズ3に進む
- 完了報告と `/create-pr` まで一気に実行する（完了後も質問しない）
- 途中停止はエスカレーション条件（前提の崩壊・fixer 不能・スコープ外変更）に該当したときのみ

以降のフェーズ1-3は detail モードの手順。simple モードの手順は末尾の「simpleモード」を参照。

<HARD-GATE>
detail では要件定義書と実装計画書を、simple では確認要約を、ユーザーが承認するまで
コードを書く・ファイルを作る・実装に着手するなどの実装行為を一切行わない。
承認後は自律実行に移行し、ユーザーへの質問なしでタスクを完遂する。
**non-stop 指定時はこの承認ゲートを自動通過する（上記の判断記録は必須）。**
</HARD-GATE>

## フェーズ1: 要件定義（detail・対話あり）

### 1. コンテキスト探索

Explore エージェントを並列活用して把握する: 関連ファイル・モジュールの構造、直近のコミット履歴、既存のテストパターン。

### 2. 要件ヒアリング

1問ずつ認識を合わせ、自律実行フェーズで迷わない解像度まで掘り下げる:

- 1メッセージ1問。回答を踏まえて次の質問を組み立てる。選択式を優先
- 聞くこと: **何を達成したいか** / **やらないこと** / **完了の定義** / **エッジケース**
- 推測できることは推測し、確認に留める（「Xという理解で合っていますか？」）
- 曖昧なまま進めない

### 3. 要件定義書の作成 + 承認

要件が固まったら要件定義書を作成し、ユーザーの承認を得る:

```markdown
# 要件定義: <タイトル>

## 目的
<何を達成するか。1-3文>

## 成功基準
- [ ] <完了条件1>
- [ ] <完了条件2>

## 機能要件
- <要件1>
- <要件2>

## 制約
- <技術的制約>
- <スコープ制約>

## やらないこと
- <スコープ外1>

## エッジケース
- <ケース1>: <対処方針>
```

- design-reviewer でレビューし、Critical があれば修正してからユーザーに提示
- `docs/specs/YYYY-MM-DD-<topic>-requirements.md` に保存
- **ユーザー承認を得てからフェーズ2へ**

## フェーズ2: 実装計画（detail・対話あり）

### 4. アプローチ検討

2-3案をトレードオフ付きで提案する（推奨案を先に、理由を添える）。ユーザーの選択を待つ。

### 5. 実装計画書の作成 + 承認

承認されたアプローチを実装計画に落とし込む:

```markdown
# 実装計画: <タイトル>

## アプローチ
<選択されたアプローチの概要>

## タスク分割

| # | タスク | 所有ファイル | テスト方針 | wave | 依存 |
|---|--------|-------------|-----------|------|------|
| 1 | ...    | ...         | ...       | 1    | なし |
| 2 | ...    | ...         | ...       | 2    | #1   |
| 3 | ...    | ...         | ...       | 1    | なし |

<各 wave の並列実行の根拠: 同一 wave 内で所有ファイルが互いに素であること>

## アーキテクチャへの影響
<依存方向・レイヤー配置の確認>

## リスク
- <リスク1>: <緩和策>
```

- 各タスクは独立してテスト可能な単位にする（コミットは wave 単位）
- **所有ファイル列と wave 列は必須**。所有ファイルは1タスクが変更を許される全ファイルを列挙する
- wave の割り当ては `references/parallel-dispatch.md` の「独立性の判定」「wave 編成」に従う
- `docs/specs/YYYY-MM-DD-<topic>-plan.md` に保存
- **ユーザー承認を得てからフェーズ3へ**（並列実行の形もこの承認に含まれる。以降 wave の
  実行順・並列度についてユーザーに確認しない）

---

## フェーズ3: 自律実行（detail・対話なし）

承認後、以下を自律的に実行する。ユーザーへの質問は禁止（迷ったら安全な選択肢を取る）。

### 6. タスク展開

`references/parallel-dispatch.md` を読む（以降の並列実行はこのプロトコルに従う）。
実装計画のタスクを TaskCreate で登録し、依存関係を TaskUpdate の addBlockedBy で設定する。
wave 列を確認し、同一 wave 内で所有ファイルが互いに素であることを再検証する
（交差していたら後続 wave に落とす。barrier で衝突するより安い）。

### 7. 実装（wave 並列 + ループ協議）

wave 1 から順に、wave ごとに繰り返す。**ユーザーへの確認は挟まない**。

1. **一括起動**: その wave のタスクを `implementer` に並列ディスパッチする
   （1メッセージ内で Agent を複数回呼ぶ。並列度上限 4）。プロンプトは
   `references/parallel-dispatch.md` の雛形どおり、必要情報を全部入れる
2. **barrier**: 全ワーカー完了後に、境界検証（`git diff --name-only` と所有ファイル集合の突合）
   → `CI_CHECK_CMD` → wave 単位のコミット、の順で実行する（`workflow.md` のループ協議は最大5回）
3. **異常系**: 失敗タスクのみ再ディスパッチ。同一エラー2回連続で fixer に委譲。
   CI が赤いときは ci-triage で分類してから直す（推測で直さない）
4. タスク完了ごとに TaskUpdate で completed にする

TDD（Red → Green → Refactor、`coding.md`）はワーカー側で回る（`.claude/agents/implementer.md`）。
オーケストレータは wave の編成と barrier に責任を持つ。
wave 内が1タスクだけになるのは正常（所有ファイルが交差する計画では直列に縮退する）。

### 8. 自律レビュー

全タスク完了後、自律的に品質検証する:

- CI 全通過を確認する（証拠を残す）
- `/self-review` スキルで品質検証する（詳細は `.claude/skills/self-review/SKILL.md`）。
  反証に成功した指摘は偽陽性として修正対象外。反証できなかった指摘のみ確定
- 確定した Critical 指摘は自律的に修正する（refactorer に委譲可）
- 修正後に再度 CI + `/self-review` を回し、確定した指摘がすべて解消されるまで繰り返す

### 9. 完了報告 + PR承認

- 全チェック通過後、コミットする
- ユーザーに完了報告する（変更サマリ、CI 通過の証拠、レビュー結果）
- **ユーザーの承認を得てから** `/create-pr` を実行し、PR URL を報告して完了

## simpleモード（確認 → 実装）

小規模・要件が明確な変更向けの軽量パス。detail との差分のみ定義する
（エスカレーション条件・証拠ファースト・品質禁止事項は共通）。

1. **確認（対話あり）**: 一問一答で要点だけ確認する（1メッセージ1問、選択式優先）。
   聞くのは最小限: **何を達成したいか** / **やらないこと** / **完了の定義**。
   エッジケースやアプローチの深掘りはしない。推測できる範囲は推測して畳む
2. **確認要約 + 承認**: 目的・やること・やらないこと・完了条件を箇条書きで提示し承認を得る
   （チャット提示のみ。`docs/specs/` への保存はしない）
3. **実装（自律・スピード重視）**: wave 編成はしないが、サブエージェントに任せられるタスクは
   積極的にディスパッチする（`implementer` を1件、または所有ファイルが明確に素なら少数の並列起動。
   出力が大きい調査・テスト実行も subagent に任せて要約だけ受け取る）。
   TDD・ループ協議は `coding.md` / `workflow.md` どおり。実装中の質問は禁止
4. **動作確認とレビュー**: `CI_CHECK_CMD` 全通過（証拠を残す）に加え、
   **動作・仕様逸脱の観点のみ**のレビューを行う（設計・スタイル・命名の指摘はしない。
   reviewer を使う場合も観点を絞る）
5. **完了報告 → 承認 → PR 作成**: detail の「9. 完了報告 + PR承認」と同じ

確認段階でスコープ拡大や判断余地の多さが判明したら、その旨を伝えて detail への切り替えを提案する。

## エスカレーション条件

以下の場合のみユーザーに確認する（自律実行の例外）:

- 要件定義・実装計画の前提が崩れた（想定外の依存、API 変更等）
- fixer エージェントでも解決できない問題（3ストライク後も失敗）
- スコープ外の変更が必要と判断した場合

## スキップ条件

以下の場合はこのスキルを実行しなくてよい:

- 質問・調査・情報確認（コードを変更しない）
- 1行の typo 修正や明らかな誤字
- ユーザーが「ブレスト不要」「すぐやって」と明示した場合
