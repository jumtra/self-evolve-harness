# 要件定義 → 実装計画 → 自律実行

3フェーズで進める。フェーズ1・2はユーザーと対話し、フェーズ3は自律実行する。

<HARD-GATE>
要件定義書と実装計画書をユーザーが承認するまで、コードを書く・ファイルを作る・実装に着手するなどの実装行為を一切行わない。
承認後は自律実行に移行し、ユーザーへの質問なしでタスクを完遂する。
</HARD-GATE>

---

## フェーズ1: 要件定義（対話あり）

### 1. コンテキスト探索

プロジェクトの現状を把握する（Explore エージェントを並列活用）:
- 関連ファイル・モジュールの構造
- 直近のコミット履歴
- 既存のテストパターン

### 2. 要件ヒアリング

細かい粒度で1問ずつ認識を合わせる。自律実行フェーズで判断に迷わない解像度まで掘り下げる:

- **1問ずつ質問する** — 1メッセージ1問。相手の回答を踏まえて次の質問を組み立てる
- 選択式を優先し、ユーザーの負荷を下げる
- 聞くべきこと: **何を達成したいか**、**やらないこと**、**完了の定義**、**エッジケース**
- 推測できることは推測し、確認に留める（「Xという理解で合っていますか？」）
- 曖昧なまま進めない。自律実行で「どっちだろう？」と迷う余地を残さない

### 3. 要件定義書の作成 + 承認

要件が固まったら要件定義書を作成し、ユーザーの承認を得る:

```markdown
# 要件定義: <タイトル>

## 目的
<何を達成するか。1-3文>

## 成功基準
- [ ] <完了条件1>
- [ ] <完了条件2>

## 機能要件
- <要件1>
- <要件2>

## 制約
- <技術的制約>
- <スコープ制約>

## やらないこと
- <スコープ外1>

## エッジケース
- <ケース1>: <対処方針>
```

- design-reviewer エージェントにレビューさせ、Critical があれば修正してからユーザーに提示する
- `docs/specs/YYYY-MM-DD-<topic>-requirements.md` に保存する
- **ユーザー承認を得てからフェーズ2へ**

---

## フェーズ2: 実装計画（対話あり）

### 4. アプローチ検討

要件定義書に基づき、2-3のアプローチをトレードオフ付きで提案する:
- 推奨案を先に出し、理由を説明する
- ユーザーの選択を待つ

### 5. 実装計画書の作成 + 承認

承認されたアプローチを実装計画に落とし込む:

```markdown
# 実装計画: <タイトル>

## アプローチ
<選択されたアプローチの概要>

## タスク分割

| # | タスク | 所有ファイル | テスト方針 | wave | 依存 |
|---|--------|-------------|-----------|------|------|
| 1 | ...    | ...         | ...       | 1    | なし |
| 2 | ...    | ...         | ...       | 2    | #1   |
| 3 | ...    | ...         | ...       | 1    | なし |

<各 wave の並列実行の根拠: 同一 wave 内で所有ファイルが互いに素であること>

## アーキテクチャへの影響
<依存方向・レイヤー配置の確認>

## リスク
- <リスク1>: <緩和策>
```

- 各タスクは独立してテスト可能な単位にする（コミットは wave 単位）
- **所有ファイル列と wave 列は必須**。所有ファイルは1タスクが変更を許される全ファイルを列挙する
- wave の割り当ては `references/parallel-dispatch.md` の「独立性の判定」「wave 編成」に従う。
  同一 wave のタスクは所有ファイルが互いに素でなければならない
- `docs/specs/YYYY-MM-DD-<topic>-plan.md` に保存する
- **ユーザー承認を得てからフェーズ3へ**（並列実行の形もこの承認に含まれる。以降 wave の
  実行順・並列度についてユーザーに確認しない）

---

## フェーズ3: 自律実行（対話なし）

承認後、以下を自律的に実行する。ユーザーへの質問は禁止（判断に迷ったら安全な選択肢を取る）。

### 6. タスク展開

`references/parallel-dispatch.md` を読む（以降の並列実行はこのプロトコルに従う）。
実装計画のタスクを TaskCreate で登録する:
- 依存関係を TaskUpdate の addBlockedBy で設定する
- 計画書の wave 列を確認し、同一 wave 内で所有ファイルが互いに素であることを再検証する
  （交差していたら後続 wave に落とす。ここで直したほうが barrier で衝突するより安い）

### 7. 実装（wave 並列 + ループ協議）

wave 1 から順に、以下を wave ごとに繰り返す。**ユーザーへの確認は挟まない**。

1. **一括起動**: その wave のタスクを `implementer` に並列ディスパッチする
   （1メッセージ内で Agent を複数回呼ぶ。既定の並列度上限 4）。
   プロンプトは `references/parallel-dispatch.md` の雛形どおり、目的・所有ファイル・完了条件・
   スコープテスト・参照ルール・前 wave の申し送りを全部入れる
2. **barrier**: 全ワーカー完了後に、境界検証（`git diff --name-only` と所有ファイル集合の突合）
   → `CI_CHECK_CMD` → wave 単位のコミット、の順で実行する（`workflow.md` のループ協議は最大5回）
3. **異常系**: 失敗タスクのみ再ディスパッチ。同一エラー2回連続で fixer に委譲する。
   CI が赤いときは ci-triage で分類してから直す（推測で直さない）
4. タスク完了ごとに TaskUpdate で completed にする

各タスクの TDD（Red → Green → Refactor、`coding.md`）はワーカー側で回る
（`.claude/agents/implementer.md`）。オーケストレータは wave の編成と barrier に責任を持つ。
wave 内が1タスクだけになるのは正常（所有ファイルが交差する計画では直列に縮退する）。

### 8. 自律レビュー

全タスク完了後、自律的に品質検証する:
- CI 全通過を確認する（証拠を残す）
- reviewer エージェントでコードレビューを実行する
- Critical 指摘があれば自律的に修正する（refactorer に委譲可）
- 修正後に再度 CI + reviewer を回す（レビューループ）
- 全指摘が解消されるまで繰り返す

### 9. 完了報告 + PR承認

- 全チェック通過後、コミットする
- ユーザーに完了報告する（変更サマリ、CI 通過の証拠、レビュー結果）
- **ユーザーの承認を得てから** `/create-pr` を実行する
- PR URL を報告して完了

---

## エスカレーション条件

以下の場合のみユーザーに確認する（自律実行の例外）:

- 要件定義・実装計画の前提が崩れた（想定外の依存、API 変更等）
- fixer エージェントでも解決できない問題（3ストライク後も失敗）
- スコープ外の変更が必要と判断した場合

## スキップ条件

以下の場合はこのスキルを実行しなくてよい:

- 質問・調査・情報確認（コードを変更しない）
- 1行の typo 修正や明らかな誤字
- ユーザーが「ブレスト不要」「すぐやって」と明示した場合
