# 設計レビュー

brainstorm スキルで作成された設計ドキュメントをレビューする。

## レビュー観点

### 1. 要件の完全性

- ユーザーの目的が設計に反映されているか
- 成功基準が明確か（何をもって「完了」か）
- スコープが明示されているか（やること / やらないこと）
- 見落とされたエッジケースがないか

### 2. アーキテクチャの妥当性

- `.claude/rules/architecture.md` の依存方向に違反していないか（フラット構造なら本項はスキップ）
- 既存のコードパターンと一貫しているか
- 適切なレイヤーにロジックが配置されているか
- 過度な抽象化（YAGNI 違反）がないか

### 3. 実現可能性

- 既存のコードベースとの統合に問題がないか
- 依存関係の追加は妥当か
- テスト可能な設計か
- パフォーマンスへの影響は考慮されているか

### 4. 仕様の品質

- プレースホルダー（TBD, TODO）が残っていないか
- セクション間の矛盾がないか
- 2通りに解釈できる要件がないか
- 影響範囲が明確か

### 5. YAGNI / KISS チェック

- 現在の要件に不要な機能が含まれていないか
- より単純なアプローチで同じ目的を達成できないか
- 過度な汎用化がないか

## 出力形式

レビュー結果を以下の形式で報告する:

### 問題点（重要度順）

各問題に:

- **重要度**: Critical（設計の根本的な問題） / Warning（改善すべき点） / Info（提案）
- **箇所**: 設計ドキュメントの該当セクション
- **問題**: 何が問題か
- **改善案**: どう修正すべきか

### 良い点

設計の強みも明記する。良い判断は強化すべき。

### 総合判断

- **承認**: 問題なし。ユーザーレビューに進んでよい
- **要修正**: Critical/Warning を修正してから再レビュー
- **要再設計**: 根本的なアプローチの見直しが必要
