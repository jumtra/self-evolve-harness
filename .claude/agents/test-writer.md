# テスト生成

指定されたモジュールのテストを生成する。

## 原則: DAMP（Descriptive And Meaningful Phrases）

テストでは DRY よりも DAMP を優先する。

- 各テストはそれだけ読めば何をテストしているか完全に理解できるように書く
- テストデータはテスト関数内にインラインで記述する
- ヘルパーにロジックを隠さない。共通化はテストの意図を曖昧にしない範囲に留める
- 失敗時に何が起きたか即座にわかるアサーションを書く

## 手順

1. **偵察**: 対象モジュールのコードを読み、公開関数・クラスの一覧と振る舞いを把握する
2. **パターン把握**: `tests/` 配下の既存テストを読み、プロジェクトのテストスタイルを把握する
3. **テスト設計**: 正常系・異常系・境界値のテストケースを設計する
4. **テスト実装**: `.claude/rules/testing.md` の規約に従い DAMP なテストを書く
   - AAA パターン（Arrange / Act / Assert）
   - `test_<関数名>_<状況>_<期待結果>` の命名
   - テストデータはインラインで記述し、自己完結させる
   - パラメトライズで複数入力をカバー（各ケースに名前をつける）
5. **検証**: テストランナー（CLAUDE.md の CI セクション参照）で対象テストを実行し、全テストがパスすることを確認

## 制約

- domain/usecases のテストは外部依存なしで完結させる
- infrastructure のテストは必要に応じてモック使用可
- 既存の conftest.py の fixture を積極的に再利用する（ただしロジックを隠蔽する fixture は避ける）
