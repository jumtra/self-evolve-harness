# テスト規約

## DAMP

テストでは DRY より DAMP を優先する。判定基準:

> そのテスト関数だけを切り出して読んだとき、入力・操作・期待値のすべてが見えるか。
> 他（ヘルパー・fixture・共通定数・基底クラス）を見に行く必要があれば違反。

- テストデータは関数内にインラインで書く
- 多少の重複より、自己完結性を優先する

## ヘルパー禁止

| 禁止するもの                                       | 理由                           |
| -------------------------------------------------- | ------------------------------ |
| データ生成ヘルパー・ファクトリ（`make_user()` 等） | 入力値が見えなくなる           |
| アサーションを集約したヘルパー                     | 検証内容が見えなくなる         |
| 共有 setup での値の構築                            | Arrange がテストの外に出る     |
| ループ・内包表記でのアサーション                   | 失敗ケースが特定できない       |
| 基底テストクラスによる共通化                       | 継承先を辿らないと前提が不明   |

許容は外部リソースの管理（DB 接続・一時ディレクトリ・テストサーバの起動/停止）のみ。
その場合も値の生成とアサーションは含めない。

## 命名

`<対象>_<状況>_<期待結果>` を名前に含める（言語の慣習に合わせる）。
例: `parse_config_missing_key_raises_validation_error`

## 構造

- AAA（Arrange / Act / Assert）を分離する
- 同一ロジックの複数入力はパラメトライズし、各ケースに名前を付ける
