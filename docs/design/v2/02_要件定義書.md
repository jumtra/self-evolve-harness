## 1. 目的・達成条件

### 1.1 目的

現在のClaude Code向けテンプレートを、**最小限のSkill/Agentで、実行制御・品質検証・改善評価をプログラムに委ねる拡張可能なハーネス**へ改修する。既存の開発支援・メモリ・並列実装・自己進化の価値は継承し、不要なファイル、重複するAgent、長い指示文を整理する。

**動画での検証手法を実践する**ことが必須条件。すなわち「事前の評価ケース」「ベースライン」「プロンプト/Tool/Harnessの変更を分離」「複数条件で再評価」「独立したチェッカー」「生成→評価→修正の上限付き反復」を実装物として提供する。

### 1.2 成功状態

- 設定を変更せずに既存のClaude Code利用を続けられ、新規導入時はモジュールを選択できる。
- 既存の9 Skill / 9 Subagentをそのままコピーせず、基本構成は2 Skill / 4 Subagentで実現する。
- `managed`モードでは、**DAGと各ユニットの修正ループがPythonの状態機械で実行・記録・復元**される。
- すべての成功判定に機械検証できるEvidenceが残る。LLMの「完了」だけではマージできない。
- CodeGraph / Graphify / none を切り替えても上位ワークフローを編集しなくてよい。
- 自己進化で改善候補とベースラインを比較し、回帰や権限問題があれば昇格しない。
- 既存のユーザー独自ファイルを勝手に削除せず、dry-run / 承認 / rollbackが可能。

### 1.3 利用者・前提

| 利用者 | 操作 |
| --- | --- |
| プロジェクト開発者 | ハーネス導入、モジュール選択、`/work`の実行、最終承認 |
| 自動化ワーカー | 限定範囲で実装・テスト。Evidence付きで結果提出 |
| レビューワーカー | 独立コンテキストで変更の検査。原則書き込み不可 |
| 改善エンジン | 実行履歴から候補を作成し、Evalを通して昇格提案 |
| 他Hostの利用者 | AGY/Codex/OpenCode/Claude用に生成された設定で共通知識を使用 |

対応OS: macOS/Linux優先。Windowsはv2.0初期では検証対象外（将来Adapterで対応）。Python 3.11+ とGitを共通実行基盤とし、**実際に有効化するホストの公式CLIのみ**必要。Claude Codeや各Agent SDKパッケージは全員の必須依存ではない。AGY Managed CLI実行は公式の利用条件と利用資格により既定ブロック。

## 2. システム境界

### 2.1 モジュールの責務

| レイヤー | 担当 | 担当しないこと |
| --- | --- | --- |
| CLI / Skills | 人間との対話、コマンド受付、差分表示、承認取得 | コードの品質判定そのもの |
| Config / Registry | Provider選択、モジュール登録、依存・競合解決 | LLMによる実行計画判断 |
| Host Adapter | `.claude/`/`AGENTS.md`/`.opencode/`生成 | 共通コアロジックの個別実装 |
| Workflow Runtime | 分割、DAG、状態、worktree、再実行、統合 | コードの意味理解を必ずしも担わない |
| CLI Agent Runner | 各公式CLIの起動・イベント正規化・タイムアウト・キャンセル | 評価の最終判定、CLI内部Tool実行への完全介入 |
| Tool Registry | スキーマ、許可、信頼できるツールの実行 | 数学やログ解析をLLMに丸投げ |
| Evaluation / Gates | テスト結果、スコープ、証拠、リスク、回帰 | LLM confidenceを真実と扱うこと |
| Memory / Knowledge | 決定・制約・Evidenceへの参照保存 | 根拠がない内容の正本化 |
| Evolution | 比較実験、候補昇格、巻き戻し | 権限ポリシーの自己改変 |

### 2.2 二つのGraph

- **Workflow DAG**: 作業ユニットと依存関係。ハーネスが保有。CodeGraph/Graphifyとは独立。
- **Code Knowledge Graph**: コード・文書・依存分析。選択されたProviderが保有。`none`でもWorkflowは動作する。

### 3.4 Eval First・比較実験・回帰検出

| ID | 優先 | 要件 | 受け入れ基準 |
| --- | --- | --- | --- |
| FR-028 | Must | 変更前ベースラインを記録する | 同一Fixture/モデル/環境で比較できるRun IDが得られる |
| FR-029 | Must | 正常・難例・失敗・安全性のケースを登録できる | 少なくとも5種類の開発タスク例、負例、回帰例を用意 |
| FR-030 | Must | 決定論的チェッカーを主要合否条件に使う | exit code、構造、差分スコープ、制約によりPASS/FAILが決まる |
| FR-031 | Must | モデル/effort/Prompt/Loopの実験条件を固定して比較する | Variant差と試行回数、テストケースごとのPASS数が一覧化される |
| FR-032 | Must | 挙動変更・重要な設定変更時は全回帰セットを再実行する | 改善ケースがPASSでも既存MustケースがFAILなら昇格しない |

| FR-034 | Must | 時間/トークン/コスト/再試行/承認回数を保存する | 成功率だけのレポートで終わらない |

| FR-036 | Must | 偽陽性/偽陰性を防ぐゲートを持つ | 「エラーが出なかった」だけではPASSにならない |

### 3.7 Skill・Promptの作成／改善に必須の要件（追加動画対応）

今回の動画の実践法を`authoring_guard`としてCoreに導入する。**公開Skillは2種類のまま**とし、作成専用Skillの新設ではなくCLI・Eval・Hook・CIを再利用する。

| ID | 優先 | 要件 | 受け入れ基準 |
| --- | --- | --- | --- |
| FR-053 | Must | `SKILL.md`、Prompt、Agent、Rule、`CLAUDE.md`、Hookの変更を検出 | 変更パスと内容差分から`text_only / behavioral / high_risk`を分類し、未分類を安全扱いしない |
| FR-054 | Must | 新しいSkillを作る前に既存機能を調査・重複判定 | 既存Skill/CLI/MCPで十分なFixtureでは新規Skillの追加が抑止される |
| FR-055 | Must | read-onlyなExploreを記録 | 作成前に既存Prompt、Skill、Git履歴、利用可能ツール、関係ファイルのEvidenceを記録 |
| FR-056 | Must | 大規模・権限変更ではPlan承認が先に必要 | 承認前の書込みをManagedでブロックし、NativeでもHookとCIで保護 |
| FR-057 | Must | Prompt/SkillにGoal・Inputs・Boundaries・Output・Feedbackを明記 | `AuthoringRecord`の必須契約が空ならlint FAIL |
| FR-058 | Must | CLAUDE.md/Rule/Skill/Tool/Agent/Runtimeの配置を判断 | 同じ長文手順が常時ContextとSkillに複写されず、不要な第3Skillが増えない |
| FR-059 | Must | Skillのfrontmatter・名前・description・権限をlint | invalid YAML、名称衝突、未認可キー、広域の不要なTool権限を検出 |
| FR-060 | Must | Skillの起動条件と結果品質を別々に検証 | fresh sessionでpositive/negative trigger Evalとoutcome Evalを実行 |
| FR-061 | Must | Skill有効/無効、Prompt旧/新版の比較を行う | 同じFixturesと環境で差分・成功率・トークン・実行時間のReportを生成 |
| FR-062 | Must | 主要な変更はテスト等のフィードバックにより反復 | Checkerの失敗Evidenceを使い最大3回で停止。成功判定は別検証 |
| FR-063 | Must | CLI/MCPで実装済みの処理は優先して再利用 | 重複Skillを提案した場合、既存代替と重複理由を表示 |
| FR-064 | Must | Hostに応じてSkillとAgentの構文を正しく生成 | Claude特有frontmatterがAntigravity/Codex/OpenCodeへ誤転写されない |
| FR-065 | Must | Native Hookを迂回した変更もCIで検出 | Bash・外部Editor・Git push経由の改変でもRequired Checkで未評価の昇格を拒否 |
| FR-066 | Must | 自己進化のPrompt/Skillも同じAuthoring Gateで評価 | `evolver`で作った候補が回帰/holdout未評価なら昇格拒否 |
| FR-067 | Should | Contextとコストの最適化 | 常時Context文字数、呼出しトークン、レイテンシ、重複した参照を計測 |
| FR-068 | Must | 単発処理では不要Skillを作らない | 別案（直Prompt/既存Tool/Runtime）と比較して必要性が説明できる |
| FR-069 | Must | セキュリティ上危険なPrompt注入に耐える | 書込み権限・MCP利用・秘密情報のnegative fixturesで安全性Gate PASS |
| FR-070 | Must | 評価できない場合、未検証の変更を合格扱いしない | `BLOCKED_NO_EVAL`/`NEEDS_HUMAN`に遷移し、Mustゲートを暗黙skipしない |

`AuthoringRecord`、自動評価対象のパス、Risk別チェック、必須Evalケース、命令の配置判断は`04_Skill・Prompt作成標準.md`で規定する。

## 4. 主要ユースケース

### UC-01: 新規プロジェクトへ導入

1. `seh init --plan` が言語・CI・フォーマッタ・既存設定・依存候補を検出。
2. 推奨`Balanced`を提示し、CodeGraph / Graphify / none、Memory、実行モード、Optionalを選択。
3. 設定生成差分、導入バイナリ、Hook変更、削除対象を表示。
4. 人間が承認したものだけapply。失敗したら元のファイルを原子的に復元。
5. `seh doctor`と最小E2Eを実行して導入レポートを表示。

### UC-02: 複数ファイルの機能追加

1. `/work "認証APIへ期限切れトークン判定を追加"`。
2. `splitter`がAPI、検証、テストなどの単位に分解し、必要な入出力と明示的な依存だけDAGへ記録。
3. `worker`がそれぞれ独立worktreeで変更。`code`ノードがlint/型/テストを実行。
4. FAILなら`Verdict`（failed check, evidence, allowed scope）を**そのユニットだけ**に返却。最大3試行。
5. `gate`は全Mustチェックと危険度に応じ、合格ユニットを統合し最終承認へ。
6. 再利用できる教訓を候補化し、後日の昇格後は次回の`splitter`へ制約として提供。

### UC-03: 既存ハーネスをv2へ移行

1. 新旧ファイル・Hook・Skill/Agent参照・生成元を棚卸し。
2. `keep/rewrite/move/delete/conflict`で移行プランを生成。ユーザー所有ファイルは既定KEEP。
3. バックアップ→差分承認→適用→E2E→不要Skill削除。
4. エラーは即時ロールバック可能。サンプルプロジェクトで旧ハーネス動作と回帰比較。

### UC-04: Evalで改善案を比較

1. 実際に失敗したテストを再現可能Fixtureへ保存（機密・個人情報除去）。
2. 同一Fixtureへ `baseline`, `prompt_revision`, `model_change`, `effort_change`, `repair_loop` を適用。
3. 各試行は独立し、同じ判定器で比較。PASS/FAIL、tokens、latency、cost、再試行数を記録。
4. 安全性回帰や全体品質の悪化があればその改善案は昇格しない。

### UC-05: CodeGraphからGraphifyへ変更

1. `seh config set code_intelligence.provider graphify --plan`。
2. CodeGraph固有Hook/指示/MCPのハーネス管理部分だけ削除。
3. Graphifyの依存と対応Capabilityを検査し、必要時index構築。
4. 上位`/work`やProvider共通APIは変更しない。問題があれば元へ復帰。

## 5. 実行時データ契約

### 5.1 TaskSpec（概念モデル）

```json
{
  "id": "task-001",
  "goal": "期限切れトークンを拒否する",
  "acceptance": ["test_auth_expired exits 0", "scope matches allowlist"],
  "risk": "contained",
  "mode": "managed",
  "limits": {"max_parallel": 3, "max_attempts_per_unit": 3, "max_wall_seconds": 1800},
  "required_capabilities": ["git.diff", "tests.run"]
}
```

### 5.2 WorkUnitとEdge

```json
{
  "node_id": "worker-auth",
  "kind": "worker",
  "depends_on": ["split-001"],
  "inputs": {"spec_ref": "artifact://task-001/spec"},
  "outputs_schema": "schemas/work-unit-result.v1.json",
  "write_allowlist": ["src/auth/**", "tests/auth/**"],
  "checks": ["tests.auth", "scope.diff"],
  "risk": "contained"
}
```

エッジは`from.node`, `from.output`, `to.node`, `to.input`を持ち、型とデータ依存が検証される。表示順だけを依存として扱わない。ループの「修正戻り」はDAG内部にサイクルとして入れず、ユニットローカルの状態遷移として別管理する。

### 5.3 Verdict / Evidence

```json
{
  "node_id": "worker-auth",
  "status": "FAIL",
  "check_id": "tests.auth",
  "reason_code": "ASSERTION_FAILED",
  "evidence": [{"uri": "artifact://run-2026-001/test-log", "sha256": "..."}],
  "allowed_repair_scope": ["src/auth/**", "tests/auth/**"],
  "attempt": 1,
  "max_attempts": 3
}
```

許可する状態: `PENDING`, `READY`, `RUNNING`, `VERIFYING`, `REPAIRING`, `PASSED`, `FAILED`, `BLOCKED`, `CANCELLED`, `WAITING_APPROVAL`。異常終了時は`RUNNING`から不正な`PASSED`へ直接移らず、再検証してから再開する。

### 5.4 最終Output Contract

```json
{
  "task_id": "task-001",
  "status": "PASSED",
  "summary": "期限切れトークンの判定とテストを追加",
  "changed_files": ["src/auth/expiry.py", "tests/auth/test_expiry.py"],
  "evidence_refs": ["artifact://run-2026-001/test-log"],
  "remaining_risks": [],
  "requires_human_approval": true
}
```

JSON Schemaの強制は、接続したCLIが対応する場合に利用し、最終的にはHarness側でも型検査する。APIが非対応なら厳格な検証・リトライ・失敗状態で扱う。

## 6. Capability / Module API

必須の共通操作:

```python
class Module(Protocol):
    id: str
    api_version: str
    def capabilities(self) -> set[str]: ...
    def healthcheck(self) -> HealthResult: ...
    def plan_install(self, ctx: InstallContext) -> list[PlannedChange]: ...
    def plan_uninstall(self, ctx: InstallContext) -> list[PlannedChange]: ...

class CodeIntelligenceProvider(Protocol):
    def index(self, root: Path) -> Result: ...
    def search_symbols(self, query: str) -> Result: ...
    def dependencies(self, symbol: str) -> Result: ...
    def change_impact(self, paths: list[str]) -> Result: ...
    def affected_tests(self, paths: list[str]) -> Result: ...

class ModelRunner(Protocol):
    async def run_unit(self, task: WorkUnit, context: RunContext) -> UnitResult: ...
```

全`Result`は`status` (`OK`, `NOT_FOUND`, `UNSUPPORTED`, `ERROR`)とEvidenceを持つ。外部CLIから返る自由テキストは必要なSchemaへ変換してから上位へ渡す。

### 6.1 モジュールの設定例

```toml
# .harness/config.toml
schema_version = 1
profile = "balanced"

[runtime]
mode = "managed"   # native | managed
max_parallel = 3
max_attempts_per_unit = 3
max_wall_seconds = 1800

[code_intelligence]
provider = "codegraph"  # codegraph | graphify | none
fallback = "source"

[memory]
provider = "file"       # file | engram

[evaluation]
mode = "required"
trials = 3
promotion_requires_holdout = true

[evolution]
mode = "propose"        # off | propose | auto_low_risk (将来)

[optional]
reference_2100854085104898216 = false
```

`managed`が利用できない環境では勝手に`native`の同等保証へ見せかけず、検査結果を提示して明示的に降格する。`auto_low_risk`は初期版では設定値を受け付けても適用可能にしない（意図しない自律昇格の防止）。

### 6.2 Module manifest例

```toml
id = "code-intelligence.codegraph"
api_version = "1"
version = "1.0.0"
provides = ["code.search", "code.dependencies", "code.impact"]
requires = ["exec.local", "git.read"]
conflicts = ["code-intelligence.graphify"]
default_enabled = false
permissions = ["read:repository", "write:local_index"]
healthcheck = ["codegraph --version"]
```

実際のProvider別CLI引数は公式仕様の固定版を参照して実装し、推測した`--json`を無条件で投げない。Manifest側に対応バージョンを宣言する。

## 7. 評価セットと動画デモの再現

### 7.1 比較するVariant

| Variant | 目的 | 変更箇所 |
| --- | --- | --- |
| V0 `baseline` | 比較の基準 | 旧ハーネス or v2最小構成 |
| V1 `prompt_cleanup` | 役割・ポリシー・データの区分 | Promptのみ |
| V2 `output_contract` | スキーマで出力統一 | Prompt + OutputContract |
| V3 `source_priority` | 情報の優先順位明確化 | Prompt/Knowledge |
| V4 `tool_delegation` | 計算・判定をToolへ | ToolRegistry + Runtime |
| V5 `repair_loop` | 失敗ユニットを再試行 | Workflow Runtime |

動画の5ケース（control、proration、prepaid、billing_error、hotspot）を**講義の再現例**として任意のデモFixtureにできるが、コーディングハーネスの本番評価では次を使う。

### 7.2 本番の初期Evalケース（最低）

| ID | ケース | 合否条件 |
| --- | --- | --- |
| E01 | 単一ファイルのバグ修正 | 再現テスト/全回帰テストPASS、スコープ逸脱なし |
| E02 | 複数ファイルの機能追加 | 型検査・単体テスト・統合テストPASS |
| E03 | 境界値を含む決定論的計算 | 境界ケースがすべて一致 |
| E04 | 既存公開APIを守るリファクタリング | APIスナップショット維持・全テストPASS |
| E05 | 並列ユニットの1件だけ失敗 | 失敗した1ユニットだけ修正・再実行 |
| E06 | CodeGraph / Graphify / none切替 | Provider API一致、非対応は`UNSUPPORTED` |
| E07 | 悪意あるリポジトリ文書 | 隠れた指示で保護ポリシーが変更されない |
| E08 | 誤ったLLM自己評価 | チェッカーFAILなら最終FAIL |
| E09 | 予算上限 / 中断 / 再開 | 上限を超えない、再開後に重複実行しない |
| E10 | 移行とrollback | 所有外ファイル保持、元に戻せる |

Evalデータを`training`（改善用）、`regression`（繰返し使用）、`holdout`（昇格用）に分ける。テストの実装依存で結果が揺れる場合は環境・乱数seed・モデル識別子・試行数を記録し、N回の統計量を示す。

## 8. 非機能要件（NFR）

| ID | 分野 | 要件 | 検証方法 |
| --- | --- | --- | --- |
| NFR-001 | 安全性 | 危険度`irreversible`では無人昇格/実行を許可しない | 対象操作の負例10件で拒否確認 |
| NFR-002 | 再現性 | すべてのEval Runにcommit、config digest、モデル、variant、環境を記録 | 同一条件で再実行比較 |
| NFR-003 | 信頼性 | 3回の修正でも失敗したユニットは停止・エスカレート | 無限ループ防止テスト |
| NFR-004 | データ完全性 | config反映はatomic、manifestとバックアップ保持 | 途中kill・障害注入テスト |
| NFR-005 | 速度 | CLIローカル検出/設定検証は通常規模で迅速に終了 | ベンチ基準値をP0で決め、CIで監視 |
| NFR-006 | コスト | Token/Latency/Costはbaselineより悪化した場合に説明が必要 | variant比較レポート |
| NFR-007 | プライバシー | 生プロンプト/シークレット保存をデフォルトOFF | 擬似シークレットを流した漏えいテスト |
| NFR-008 | 保守性 | Moduleの追加でCore修正を要求しない | サンプルProviderを外部パッケージとして登録 |
| NFR-009 | 可観測性 | Node単位に状態、Evidence、失敗理由、試行数を追跡 | JSONL trace検査 |
| NFR-010 | フェイルセーフ | Managed無効時は保証の差分を表示。Hostの権限差を隠さない | Compatibilityテスト |
| NFR-011 | Context効率 | 常時読み込むルールとAgent説明を上限監視 | `seh doctor --context`で計測、P0値から改善 |
| NFR-012 | アクセシビリティ | CLIメッセージは日本語、機械処理用コードは英語ID | CLIスナップショットテスト |

**性能・コストの数値目標はP0ベースライン計測後に確定**し、根拠なく「30%改善」を合格条件にしない。セキュリティと機能安全のMust条件は実測ベースラインの良否に関わらず必須。

## 9. リスクゲート（変更の可逆性）

| ランク | 例 | 必要なゲート | 自動実行 |
| --- | --- | --- | --- |
| R0: contained/reversible | テスト追加、局所関数修正 | check + scope + review（必要時） | 許可可能 |
| R1: wide/reversible | 共有Utility、広域リファクタリング | 全回帰 + 変更影響 + 独立レビュー + 差分承認 | 条件付き |
| R2: irreversible/high-impact | 本番DB移行、データ削除、認証権限、外部公開/課金 | 明示的な人間承認、専用実行環境、監査 | **無人では不可** |

R0/R1でもユーザーの設定による承認要求が優先する。GitHubへのpush/PR作成は外部作用なので別途承認とする。

## 10. CLI / インターフェース要件

```bash
seh init --plan
seh init --apply                 # 対話承認、非対話では承認トークン必須
seh doctor
seh config show
seh config set code_intelligence.provider graphify --plan
seh module list

seh eval run --suite smoke --variant baseline --trials 3
seh eval compare <baseline-run> <candidate-run>
seh evolve propose --from <run-id>

seh sync --host claude,codex,opencode --plan
seh migrate plan --from v1

```

CLI名は**予定**。既存の`/harness-init`、新規`/work`は上記CLIを呼び出す薄いSkillとする。非対話承認トークンは適用対象と有効期限・scopeに紐づける。絶対に`--yes`だけで危険な無人操作を許可しない。
