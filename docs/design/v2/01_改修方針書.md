## 0. 結論／設計判断

**機能を足す前に、既存のSkill・Agent・Rule・Hookの重複を取り除く。** そのうえで、動画で実演された **Eval-first / Prompt・Tool・Harnessの分離 / Generate→Evaluate→Repair / 複数方式の比較実験** と、指定X投稿の **ノード内の検証ループ・ノード間のDAG・証拠付きゲート・学習の戻り経路** をソフトウェアとして実装する。

基本構成の目標は **公開Skill 2種、カスタムSubagent 4種、共通Rule 2〜3ファイル**。あくまで最小構成であり、機能拡張時には必要なモジュールだけ追加する。**記憶や自己進化の機能そのものは削除しない。**

### 設計原則

1. **削除優先**: Claude Code標準機能と重複するSkillは削除する。専門能力に再利用価値があれば後からモジュール化する。
2. **決定論をコード化**: 差分チェック、依存解決、テスト、重複排除、アクセス許可、昇格判定はプログラムで実施。モデルの「できました」は合格証拠にならない。
3. **Skill = 入り口、Runtime = 制御**: Markdownの手順書だけで実行保証を謳わない。タスク制御が必要なときはプログラムのオーケストレータを使う。
4. **一度に一つの責務**: 各ワークユニットに入力・出力・編集範囲・検証条件を与える。失敗時は当該ユニットだけ再実行する。
5. **Eval First**: 振る舞いを変える前に、代表例・負例・回帰例・ホールドアウト例を用意する。
6. **安全な自己進化**: 提案→独立評価→承認→昇格→ロールバック。信頼境界・承認ポリシー自体はAIが自己変更できない。
7. **選択可能な依存**: CodeGraph / Graphify / none、File / Engram、オプション機能をセットアップ時に選択する。
8. **生成物を識別**: ハーネス生成ファイルだけを管理し、ユーザーが作成した設定やSkillは勝手に削除しない。
9. **4ホスト対等**: Claude Code / Google Antigravity（AGY）/ Codex / OpenCodeの共通仕様を`.harness/spec/`に保ち、各Host Adapterで生成する。ホストごとの機能差は明示する。
10. **CLI First / SDK Optional**: Claude/Codex/OpenCodeは公式CLIを標準実行手段とし、SDKパッケージを本体・Managed Runtimeの必須依存にしない。AGYのManaged実行は利用規約上の利用資格確認を要する。HostごとのCapabilityを検出し、不可時は明示的に停止する。
11. **Prompt/SkillはEvidence-gated Authoring**: 新規作成と編集をread-only探索→配置判断→計画→評価セット→変更→fresh sessionで検証→比較→昇格に通す。`seh author`（Core）とCIで保証し、専用の公開Skillは増やさない。
12. **コストを測る**: 成功率だけでなく、経過時間、使用量、失敗・再試行数、手動承認数も比較する。

## 5. 動画の実践内容をどこに置くか

アップロード動画「The prompting playbook」（約33分24秒）の画面と字幕を確認。内容は概ね次の2シナリオである。

### シナリオA: 既存サポートBotの段階改善

- 事前に5ケース × 6試行のような複数回評価セットを用意し、コントロールケースと失敗モードを可視化。
- v0→v1: 長大なプロンプトを役割・ルール・データ等に整理。別ケースに回帰が出る。
- v1→v2: 最終応答に`<reply>`契約を設け、ハーネス側にstop sequenceと抽出を追加。
- v2→v3: 情報源の優先順位を明確化し、古いポリシーの過度適用を抑制。
- v3→v4: 日割り計算を暗算させず`calculate_proration`ツールで実装し、API側でToolループを回す。
- v4→v5: 課題ごとのエスカレーション指示を適切な境界へ調整。各版ごとに全ケースを再評価。

**導入方法**: これを「会話型サポートBotを内蔵する」こととは解釈しない。コーディングハーネスに `eval_runner`・`output_contract`・`tool_registry`・`prompt_versioning` として組み込む。動画の通り固定文字列のタグ＋stop sequenceを再現できる`api_text` Adapterも用意するが、標準は**スキーマ付きJSONの返答とプログラム検証**。標準CLIでstop sequenceを使えない場合に擬似的な停止保証を主張しない（低レベルAPI Adapterは将来の任意モジュール）。隠れた推論本文の出力は要求せず、必要なのは短い判断理由／実行証拠のみ。

### シナリオB: シフト作成Agentの比較

- 同じ制約を持つ課題を、単純プロンプト、モデル変更、推論量変更、プロンプト改善、Generate→Evaluate→Repairで比較。
- チェッカーは「重複シフトなし」「各人の勤務上限」等をプログラムが判定。構造化出力は人間が後から解釈する文章ではなく機械処理可能な形。
- 正解率だけでなく、レイテンシとトークン量のトレードオフを観察。

**導入方法**: `eval/`を先に作り、同一のコーディング課題に対する `baseline`, `prompt_only`, `strong_model`, `higher_effort`, `generator_evaluator_repair` を比較。実行ランは固定したモデル識別子・ワークツリー・テストスイート・試行回数とともに記録。**「動画でループが良かった＝すべての課題でループを実行」はしない。**

### 5.1 追加動画から導入する「Prompt/Skillを正しく作る方法」

追加動画（Boris Cherny講演、約27分）はClaude Codeの構成・使い方の実践講演であり、Skill生成の自動採点方式自体を直接説明するものではない。ハーネスへの設計変換は以下:

- **まずQ&Aで既存コードを理解**: Skill/Prompt変更の前にread-only探索・Git履歴・既存Skillとの重複を検証する。
- **大きな作業はPlanを先に**: 対象/目的/成功条件/ツール/承認を具体化する。小変更は過剰な承認手順を省略可。
- **CLI/MCPを再利用**: 適切な既存CLIやMCPがあるなら、同じ処理をSkillやPromptに長文再実装しない。
- **Contextの階層化**: `CLAUDE.md`は短い全体ルール、path-scoped Rulesは局所ルール、Skill本文はオンデマンドで読み込む。
- **評価できる道具を与える**: テスト/型検査/スクリーンショット/構造チェッカーを与え、上限付きで修正する。
- **構造化結果・分離実行**: 公式CLIのJSON/JSONL出力契約と、必要時のgit worktree並列を使う。SDKパッケージは要求しない。

これらを前回動画のEval-first・Prompt/Tool/Harness分離・比較実験と結合した**`authoring_guard`**をCoreに追加。Claude Codeの標準Skills/commandsの機能と重複する第3の作成Skillは作らず、`/work`→`seh author`（内部CLI）→CIで評価ゲートを適用する。詳細は`04_Skill・Prompt作成標準.md`。

## 6. X投稿（Loop & Graph）を実装する

元記事: https://x.com/hanakoxbt/status/2091515787366306154 （キャッシュ全文を確認）。導入要件:

- **ノード種別**: `splitter` / `worker` / `code` / `gate`。
- **明示的な依存関係**: あるノードが前のノードの出力値を必要とするときだけエッジを張る。
- **局所ループ**: 各workerが `produce -> deterministic check -> repair` を最大3回。失敗は当該ユニットへ返す。
- **Mergeと境界**: 独立worktreeの差分を競合検査し、成功ユニットだけ取り込む。
- **二つの戻り経路**: `correction_edge` は現在のタスクの失敗修正、`learning_edge` は認定された制約を次回の分割計画へ反映。
- **リスク基準の承認**: モデルの自信ではなく可逆性・変更範囲を用いて判定。不可逆操作は人間の明示承認なしでは通過させない。

動画でのGenerate/Evaluate/Repairは**各ノード内部**、X投稿のGraphは**ノード同士の外側**、と整理する。

## 7. 実行モード（v1.3: CLI First / SDK Optional）

**Agent SDKのPython/TypeScriptパッケージは導入しないことを標準とする。** 「Claude Codeの`claude -p`が公式資料上Agent SDK CLIと呼ばれる」ことと、「開発者向けPython/TypeScript SDKを追加インストールする」ことは別概念。前者はCLIとして利用し、後者を必須要件にしない。

| モード | 実行 | 保証と制約 |
| --- | --- | --- |
| `native`（初期設定） | 開発者が選択ホストの標準UI/CLIで通常作業し、`seh`が設定生成・評価・CIを担当 | 実行中の逐次介入はホスト依存。完了時に独立検証 |
| `managed`（SDK不要） | Python `WorkflowEngine` → `CliAgentRunner` → 公式CLIの1ユニット実行 → 独立検証・再試行 | DAG・試行回数・予算・checkpoint・成果物隔離はHarnessが制御。**モデル内部の個別Tool呼出しの完全介入は保証しない** |
| `sdk`（将来の任意プラグイン） | CLIで必要な機能が提供されず、SDKの価値と権限を事前評価できた場合のみ追加 | 既定OFF。CLI版と契約テストを共有。Coreの依存には入れない |

`managed`は**SDKではなくCLIをラップする外側のオーケストレーション**である。CLI呼出しには配列argv、限定cwd/env、タイムアウト、終了・キャンセル、stdout/stderr分離、JSON/JSONLパース、権限設定と隔離worktreeを用いる。終了コード0だけではPASSとせず最終イベント、パーサ結果、テスト、Git diff、Policyを検証する。

Hostごとの標準CLI: Claude `claude -p`、Codex `codex exec`、OpenCode `opencode run`、Antigravity `agy -p`（**コンシューマープラン上の外部ラッピング禁止に注意**）。AGYは設定/Skill出力を提供するが、外部Managed実行は既定`POLICY_BLOCKED`とし、当該契約で利用が認められることを確認できた場合に限り有効化できる。許可外の自動ラッピング・アカウント切替は実装しない。

API/SDK特有の低レベル`stop`やTool callbackはCLIで再現できないと明記する。動画の原理（定量評価、計算のコード委譲、構造化結果、生成→評価→修正）はCLIで実装する。

## 8. 新しい拡張アーキテクチャ

```text
Host (Claude / AGY / Codex / OpenCode)
    ↓ HostAdapter (native config) / CliAgentRunner (managed execution; AGY policy-gated)
Skills (harness-init, work)  ← 4ホストへ生成する2つの論理Skill
    ↓
Harness Core (CLI, Config, Registry, Capability Resolver, Policy, Events)
    ├─ Workflow Runtime (DAG, bounded loop, worker, merge, checkpoint)
    ├─ Tool Registry (JSON Schema + trusted implementations + audit)
    ├─ Evaluation (fixtures, deterministic checker, variants, holdout, report)
    ├─ Code Intelligence (CodeGraph | Graphify | None)
    ├─ Memory (File | Engram)
    ├─ Evolution (observe, propose, benchmark, approve, promote, rollback)
    ├─ Authoring Guard (Skill/Prompt explore, lint, eval, compare, promote)
    └─ Integrations (git, PR, opt-in extras)
```

- **Capability契約**で機能を発見する。モジュールは他モジュールの具体的なディレクトリに依存せず`code.search_symbols`などを要求する。
- **Module manifest**にID/APIバージョン/提供機能/依存/競合/初期値/許可/チェック/解除手順を記載。
- **外部ツール導入は二段階**: dry-runで実行予定コマンドと書込先を見せ、承認後にinstall・healthcheck・restoreを実施。`curl | sh`を自動で実行しない。
- **所有権manifest**が設定生成の出所・hash・過去バージョンを管理。既存ユーザー変更があれば三者差分を表示する。
- **Provider = Capability**。CodeGraphとGraphifyは互換ではないため、未対応操作は`UNSUPPORTED`を返し、フォールバック規約に従う。コード知識グラフとWorkflow DAGを混同しない。

## 9. CodeGraph / Graphify 選択

`code_intelligence.provider = "codegraph" | "graphify" | "none"` を初期化画面とconfigに公開。

- **CodeGraph**: `colbymchenry/codegraph`。ローカルのコードシンボル/依存・影響解析を主な利用目的とする。
- **Graphify**: 正式候補として **`Graphify-Labs/graphify`**（コード・文書・SQLスキーマ等のグラフ化）を採用。**`EaZtoday/graphifyy`は別プロジェクト**なので名称を混同せず、必要なら後日`graphifyy` Adapterとして追加する。
- **None**: `git`, `rg`, `ast`等のフォールバック。使えない解析を「結果ゼロ」と扱わず警告する。

`CodeIntelligenceProvider`の機能: `index`, `search_symbols`, `dependencies`, `change_impact`, `affected_tests`, `healthcheck`。`affected_tests`など未対応の機能は`UNSUPPORTED`で返す。Graphifyが外部で生成するSkill/Hookはそのまま二重導入しない。**本体CLIクエリをProvider Adapter経由で呼び、設定生成はHarness側が責任を持つ。**

## 11. セキュリティと自己進化の境界

- 評価対象のSkill、リポジトリ文章、外部検索は**非信頼データ**。命令として自動実行しない。
- 生成されたコードは隔離されたworktreeで実行。CI用の認証情報や本番データへ原則アクセスさせない。
- `evolver`はレビュー前の生成物に直接書き込まない。候補変更は別worktreeに隔離。
- **高リスク変更**（セキュリティ・権限・データ削除・課金・本番デプロイ・認証）は、人間承認が必須。成功率やLLM confidenceで自動解除しない。
- シークレット検査は正規表現だけに依存しない。Git差分検査、git-secrets等（選択制）、ホスト/CIでの最終チェックを併用する。
- 永続化するテレメトリから秘密情報と生のユーザーデータを除き、保管上限と削除手段を設ける。

## 12. 削除・移行の原則

1. 現状をテスト付きで凍結（Git tag, checksum, インベントリ）。
2. `/harness-init`、`/brainstorm`等の全参照を調べる。削除可能な対象は**テンプレートが管理するものに限定**する。
3. `seh migrate plan`で `KEEP / REWRITE / MOVE / DELETE / USER_OWNED_CONFLICT`を列挙。
4. バックアップ、差分表示、承認、原子的書き込みを経て適用する。
5. 新しいRule・Hook・Provider・Agentが実際に稼働するE2Eを確認してから古いものを削除する。
6. `seh migrate rollback <snapshot>`で移行前へ復元できることをテスト。
7. 旧Skill参照切れ、重複Hook、生成ファイルの意図しない上書きがゼロであることを検証。

## 13. 対象外（v2.0初期リリース）

- 各公式CLI内で動くLLM推論/Tool使用ループの独自フル再実装。
- 全モデル・全ホストで同じ権限/Hook機能を実現できるという保証。
- 自動課金・本番操作・リポジトリの無条件自動マージ。
- フル機能のWebダッシュボード（JSON/Markdown/HTMLレポートで十分）。
- 2件目X投稿の内容が確定する前の実体機能の推測実装。
- すべてのAI生成Skillの自動保存。Evalを通過したものだけ昇格する。

## 13.1 Skill/Prompt変更の特別扱い

`SKILL.md`、`.claude/agents/*.md`、プロンプト、`CLAUDE.md`、Rule、Hook定義に差分がある場合は「通常コード変更」だけで閉じない。影響範囲とリスクを分類し、**Behavioral変更はfresh-sessionのpositive/negative + regression Eval**、権限・安全ルールの変更は人間承認を要求する。NativeはHookで早期検出、**最終的にはCIの必須Gate**で抑止する。何も検証できなかった場合を「成功」と記録しない。

## 15. v1.3 差分・SDK非必須化

- `HostAdapter`（設定生成）と`CliAgentRunner`（プロセス起動）と`VerificationGate`（成果物判定）を分離。
- **全4ホストでSDKパッケージ不要**という設計を採用。ただし、AGYは第三者アプリからのラッピングがコンシューマープランで未サポートのため、設定生成可能とManaged実行可能を厳密に区別する。
- `native`と`managed`のどちらでも独立評価・CIは共通。`managed`でのみ外側のDAG/局所ループ/予算を強制する。
- CLIの構造化出力・パーミッション・サンドボックスはホスト差があるため、単一のフラグを全ホストに渡さない。
- SDKは将来の任意アダプターとして追加可能だが、デフォルト依存、インストール、テスト前提から削除。
- 詳細は `06_CLIランナー・SDK任意化設計.md` を正式な実行契約とする。
